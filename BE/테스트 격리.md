각 테스트가 서로 독립적으로 실행되어 다른 테스트의 상태나 결과에 영향을 주고받지 않도록 보장하는 것을 말합니다.

## 왜 필요한가

- 격리가 깨지면 실행 순서나 공유 자원 상태에 따라 결과가 달라지는 **비결정적(Non-deterministic) 테스트**가 발생합니다.
- 비결정적 테스트는 실패했을 때 원인이 실제 코드 버그인지 격리 문제인지 구분하기 어려워 신뢰도를 떨어뜨립니다.
- [[단위 테스트]]는 Mock으로 의존성을 대체해 격리가 비교적 쉽지만, [[통합 테스트]]는 DB 같은 공유 자원을 사용하므로 별도의 격리 전략이 필요합니다.

## Spring에서 DB를 공유하는 테스트를 격리하는 방법

|방법|동작 방식|단점|
|---|---|---|
|`@DirtiesContext`|테스트마다 애플리케이션 컨텍스트를 새로 로드|컨텍스트 재생성 비용이 커서 느림|
|`@Sql`로 TRUNCATE|테스트 전후 스크립트로 테이블을 초기화|테이블이 추가될 때마다 스크립트 유지보수 필요|
|`@Transactional` 롤백|테스트 종료 후 트랜잭션을 롤백해 상태를 복원|아래 주의사항 참고|

```java
@DirtiesContext(classMode = DirtiesContext.ClassMode.AFTER_EACH_TEST_METHOD)
@SpringBootTest
class MyIntegrationTest {
}
```

## @Transactional 롤백 방식의 주의사항

- OSIV를 끄고 [[@Transactional]] 없이 지연 로딩 엔티티를 조회하면 프로덕션에서는 LazyInitializationException이 발생하지만, 테스트에서는 트랜잭션이 열려 있어 예외 없이 통과하는 **거짓 음성(False Negative)** 이 나타날 수 있습니다.
- `@SpringBootTest`의 WebEnvironment가 `DEFINED_PORT`/`RANDOM_PORT`이면 별도 스레드에서 서블릿 컨테이너가 실행되어 테스트 트랜잭션 롤백이 적용되지 않습니다.
- 전파 속성이 `REQUIRES_NEW`인 메서드는 새 트랜잭션을 생성하므로 테스트 트랜잭션과 무관하게 커밋됩니다.
- 비동기 메서드는 별도 스레드에서 실행되므로 롤백 대상에 포함되지 않습니다.

## 핵심 정리

테스트 격리는 테스트 간 독립성을 보장해 비결정적 결과를 방지하는 것이며, Spring 통합 테스트에서는 컨텍스트 재생성, 테이블 초기화, 트랜잭션 롤백 중 상황에 맞는 전략을 선택하되 각 방식의 한계를 이해해야 합니다.
