데이터의 최종 상태를 저장하는 대신, 상태를 변경시킨 이벤트들의 이력을 저장하고 이를 재생(replay)하여 현재 상태를 복원하는 아키텍처 패턴입니다.

## 핵심 개념

전통적인 상태 저장 방식과 비교하면 차이가 분명합니다.

|방식|저장 대상|상태 조회 방법|
|---|---|---|
|**상태 저장 (전통적 방식)**|최종 상태 그 자체|테이블에서 바로 조회|
|**이벤트 소싱**|상태를 변경시킨 이벤트 목록|이벤트를 처음부터 순서대로 재생(replay)|

예를 들어 체스판의 상태를 저장할 때, 상태 저장 방식은 각 칸의 말 배치를 그대로 저장하지만 이벤트 소싱은 "검은색 폰이 1a로 이동했다"와 같은 기보(이벤트)를 순서대로 저장합니다. 현재 상태는 저장된 이벤트를 순서대로 재생해 계산합니다.

## 동작 원리

```
이벤트 발생 → 이벤트 스토어에 append-only로 저장
           → 조회 시 이벤트를 순서대로 replay
           → 최종 상태 도출
```

- 이벤트는 **수정되거나 삭제되지 않고 추가만** 됩니다(append-only).
- 매번 전체 이벤트를 재생하는 비용을 줄이기 위해, 특정 시점까지의 계산 결과를 저장해두는 **스냅샷**을 활용할 수 있습니다.

## 장단점

|장점|단점|
|---|---|
|모든 시점의 상태를 재현 가능 (감사 추적, 디버깅에 용이)|이벤트를 모두 재생해야 하므로 읽기 성능이 저하될 수 있음|
|비즈니스 로직 변경 시 새로운 규칙으로 이벤트를 재생해 대응 가능|이벤트가 계속 추가되므로 대용량 데이터 처리 필요|
|특정 문제 상황의 재현과 테스트가 용이|스냅샷 등 추가 설계 없이는 조회 성능 확보가 어려움|

## 관련 패턴

- 명령과 조회 모델을 분리하는 [[CQRS]]와 함께 사용되는 경우가 많습니다. 이벤트 소싱으로 명령(상태 변경)을 처리하고, CQRS의 조회 모델은 이벤트로부터 미리 계산된 뷰를 제공합니다.
- 비즈니스 로직 실행과 이벤트 발행을 하나의 트랜잭션으로 묶는 [[Outbox 패턴]]과는 목적이 다릅니다. Outbox 패턴은 메시지 유실 방지가 목적이고, 이벤트 소싱은 이벤트 자체를 상태의 원천(Source of Truth)으로 삼는다는 차이가 있습니다.

## 핵심 정리

- 최종 상태 대신 상태를 변경시킨 이벤트 이력을 저장하고, 재생(replay)하여 현재 상태를 도출하는 방식
- 과거 상태 재현과 비즈니스 로직 변경에는 유연하지만, 읽기 성능과 데이터량 측면에서는 트레이드오프가 있음
