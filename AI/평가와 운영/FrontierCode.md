FrontierCode는 코딩 에이전트가 만든 코드 변경이 "테스트를 통과하는가"가 아니라 "사람이 손대지 않고 그대로 머지될 수 있는가"를 기준으로 채점하는 코딩 에이전트 벤치마크다.

기준 시점: 2026-11

## 왜 필요한가

코딩 에이전트를 재는 가장 흔한 방법은 숨겨둔 테스트를 돌려 통과 여부를 보는 것이다. 자동화하기 쉽고 결과가 이진이라 비교도 편하다. 문제는 **테스트 통과와 머지 가능은 다른 사건**이라는 점이다.

```
과제: "날짜 파싱 버그를 고쳐라"

패치 A:  파싱 함수 2줄 수정 + 회귀 테스트 1개             → 테스트 통과
패치 B:  같은 2줄 수정 + 근처 모듈 리팩터링 + 포매터 전체 적용 → 테스트 통과
패치 C:  테스트 케이스를 특수 처리하는 분기 추가               → 테스트 통과

테스트 기준 점수:   A = B = C = 통과
리뷰어가 머지하는가: A만 머지, B는 범위 밖 변경으로 반려, C는 꼼수로 반려
```

테스트만 보는 채점은 B와 C를 A와 구분하지 못한다. 실제 팀에서는 B 같은 패치가 더 골치다. 내용이 좋아도 리뷰 범위가 커지고 충돌이 늘어 결국 사람이 쪼개거나 되돌려야 하기 때문이다. 에이전트를 팀에 붙였을 때 체감되는 유용성은 "리뷰어가 손을 몇 번 대야 하는가"에 더 가깝고, FrontierCode는 그 축을 직접 재려는 시도다. [[에이전트 평가]]에서 최종 답만 보지 말고 궤적을 보라고 한 것과 같은 문제의식이 코드 쪽으로 옮겨온 것이다.

## 무엇을 재는가

이 노트에서 확인한 범위는 앤트로픽의 모델 발표 페이지에 실린 설명과 각주까지다. 벤치마크를 만든 쪽의 원문 사양은 받아오지 못했다.

- **채점 기준은 "사람 수정 없이 머지될 수 있는가"다.** 앤트로픽은 Claude Sonnet 5.5 발표 각주에서 "FrontierCode는 코드 변경이 사람의 수정 없이 머지될 수 있는지를 평가한다"고 설명한다.
- **범위 밖 변경은 감점된다.** 같은 각주는 "품질이 높거나 도움이 되는 변경이라도 범위를 벗어나면 감점한다"고 밝힌다. 위 예시의 패치 B가 깎이는 이유다.
- **만든 곳.** 같은 각주에 "Cognition이 검토한 두 사례"라는 표현이 나와, 채점과 사례 검토를 Cognition이 맡는 것으로 보인다. FrontierCode는 Devin을 만든 Cognition의 벤치마크로 알려져 있다.
- **버전과 세트가 있다.** 앤트로픽 발표들은 `FrontierCode v1.1 (Main)`처럼 버전과 세트 이름을 붙여 점수를 낸다. Claude Fable 5.2 발표에서는 FrontierCode 2.0 점수를 인용한다. 버전이 다르면 과제와 채점이 달라질 수 있으니, 숫자를 비교할 때는 버전과 세트부터 맞춰야 한다.

### 점수는 비용과 같이 읽는다

앤트로픽 발표들은 FrontierCode 점수를 하나의 숫자가 아니라 **"작업당 비용 대비 점수" 그래프**로 보여준다. 같은 모델을 [[Effort 설정|effort]] 단계(Low~Max)별로 돌려 점 여러 개를 찍는 방식이다.

```
 점수
  ▲
  │                 ● Xhigh
  │            ● High      ● Max      ← Max가 Xhigh보다 낮다
  │       ● Medium
  │  ● Low
  └──────────────────────────────▶ 작업당 비용 (로그 스케일)
```

이렇게 그리면 "최고 점수"보다 "같은 점수를 얼마에 내는가"가 먼저 보인다. 예를 들어 앤트로픽은 Claude Opus 5.5가 기본(medium) effort에서 54.6%를 기록해 GPT-6 Astra의 최고점 53.3%를 작업당 비용 약 5분의 1로 넘었다고 밝혔다.

## 사례: effort를 올렸더니 점수가 내려갔다

Claude Sonnet 5.5 발표의 FrontierCode v1.1(Main) 결과에서 Sonnet 5.5는 Max effort(46.2%)가 Xhigh effort(52.1%)보다 낮았다. 앤트로픽이 각주에 적은 원인은 이렇다.

- Max effort에서 Sonnet 5.5가 Claude Code의 코드 리뷰 스킬을 더 자주 실행했다.
- 그 스킬은 리뷰를 여러 서브에이전트로 나눠 돌린다.
- Cognition이 검토한 두 사례에서 이것이 **타임아웃**으로 이어지거나, **과제 범위를 넘는 추가 수정**으로 이어져 점수가 낮아졌다.

```
Max effort
  └─ "더 꼼꼼히" → 코드 리뷰 스킬 실행
        └─ 리뷰를 서브에이전트 여러 개로 분할
              ├─ 시간 초과                 → 실패
              └─ 리뷰 지적을 반영해 추가 수정 → 범위 밖 변경 → 감점
```

이 사례가 보여주는 것은 두 가지다. 첫째, 테스트 기준이었다면 "추가로 고친 것"은 감점 사유가 아니었을 테니 이 차이 자체가 드러나지 않았다. 둘째, 더 많이 생각하고 더 많이 검토하는 것이 언제나 좋은 패치로 이어지지는 않는다. 리뷰 단계가 [[서브에이전트와 컨텍스트 격리|서브에이전트]]로 퍼지면 시간 예산을 먹고, 리뷰가 찾아낸 "개선점"이 그대로 범위 확장이 된다.

## 내 에이전트에 가져올 것

FrontierCode 점수를 직접 돌리지 않더라도, 코딩 에이전트를 만들 때 채점 기준을 "머지 가능"에 가깝게 옮기는 건 해볼 수 있다.

- **테스트 통과는 필요조건으로만 둔다.** 통과한 패치에 한해 범위·스타일·테스트 품질을 따로 본다.
- **범위 위반을 별도 항목으로 잰다.** 과제와 무관한 파일을 건드렸는지, 변경 줄 수가 과제 크기에 비해 과한지 같은 것은 diff만으로 상당 부분 자동 판정할 수 있다.
- **사람 판단이 필요한 항목은 루브릭으로 쪼갠다.** "머지할 만한가"를 한 번에 묻지 말고 항목별로 물어야 [[LLM-as-judge]]로 돌릴 때도 흔들림이 줄어든다. 판정 모델의 기준은 실제 리뷰어가 반려한 PR 몇 개로 먼저 맞춰본다.
- **effort와 리뷰 단계는 실측해서 고른다.** 위 사례처럼 높은 effort가 자동으로 리뷰·재작업 루프를 부르면 결과가 오히려 나빠질 수 있다. 시간 제한과 "과제 범위 밖은 고치지 말고 메모로 남긴다" 같은 지시를 함께 둔다.

## 트레이드오프

- **채점 비용이 크다.** 테스트 실행은 기계가 하지만 "머지할 만한가"는 사람이나 판정 모델이 봐야 한다. 과제 수를 늘리기 어렵고 채점 결과의 분산도 커진다.
- **좋은 변경을 깎는다.** 범위 밖 변경을 감점하므로, 실제로는 고맙게 받았을 리팩터링도 점수에서는 손해다. 이 벤치마크는 "시킨 일만 정확히 하는 에이전트"를 높게 친다는 뜻이고, 그게 내 팀의 기준과 같은지는 따로 확인해야 한다.
- **시간 제한이 결과를 좌우한다.** 타임아웃이 실패로 처리되면 오래 검토하는 설정이 불리해진다. 점수 차이가 능력 차이인지 시간 예산 차이인지 구분해서 읽어야 한다.

## 주의사항

- **버전·세트를 섞어 비교하지 않는다.** v1.1 Main 점수와 2.0 점수는 다른 시험이다.
- **발표 자료의 점수는 그 회사가 고른 설정이다.** effort 단계별 곡선을 같이 공개하는지, 최고점만 내세우는지 확인한다.
- **벤치마크의 감점 기준이 내 기준과 다를 수 있다.** 범위 밖 변경을 환영하는 팀이라면 FrontierCode 점수 순위가 체감과 어긋날 수 있다.

## 핵심 정리

- FrontierCode는 "테스트 통과"가 아니라 "사람 수정 없이 머지 가능"을 채점한다.
- 범위를 벗어난 변경은 품질이 좋아도 감점된다.
- 앤트로픽은 점수를 effort별 비용 대비 곡선으로 낸다. Sonnet 5.5는 Max effort에서 리뷰 서브에이전트로 인한 타임아웃·범위 밖 수정 때문에 Xhigh보다 낮았다.
- 내 코딩 에이전트에도 "테스트는 필요조건, 범위·스타일은 별도 항목"이라는 채점 구조를 가져올 수 있다.
