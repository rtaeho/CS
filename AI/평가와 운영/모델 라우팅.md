요청마다 어떤 모델이 처리할지를 고르는 설계로, 쉬운 요청은 값싼 모델에 보내고 어려운 요청만 비싼 모델에 보내 품질을 크게 잃지 않으면서 비용을 줄이는 것이 목적이다.

기준 시점: 2026-11

## 왜 필요한가

에이전트에 들어오는 요청의 난이도는 고르지 않다. "이 문장을 영어로 바꿔줘"와 "이 레포의 동시성 버그를 찾아줘"가 같은 엔드포인트로 들어온다. 모든 요청을 가장 강한 모델로 보내면 품질은 안전하지만, 대부분의 쉬운 요청에 필요 이상의 돈과 지연을 쓴다. 반대로 전부 작은 모델로 보내면 어려운 요청에서 실패한다.

에이전트에서는 이 차이가 더 커진다. 한 작업이 수십 번의 모델 호출로 이루어지고, 그중 상당수는 파일 읽기 결과를 요약하거나 다음 툴을 고르는 정도의 단순한 단계다. 정말 판단이 필요한 단계는 몇 번뿐이다. 그 몇 번을 위해 나머지 전부를 비싼 모델로 돌리는 것이 낭비라는 게 라우팅의 출발점이다.

## 라우팅의 세 가지 형태

```
1) 사전 라우팅 (router)         2) 캐스케이드 (cascade)          3) 에스컬레이션 (advisor)
   요청 ─▶ 라우터 ─┬▶ 작은 모델     요청 ─▶ 작은 모델 ─▶ 답         작은 모델이 루프를 돈다
                  └▶ 큰 모델                 │ 검사 통과?              │
   호출 전에 난이도를 예측                     ├ 예 ─▶ 반환             ├ 막히면 큰 모델에 자문
                                             └ 아니오 ─▶ 큰 모델        └ 조언 받고 계속 진행
```

- **사전 라우팅** — 요청을 보내기 전에 분류기가 난이도를 예측해 한 모델을 고른다. 호출이 한 번이라 지연이 늘지 않지만, 예측이 틀리면 그대로 품질이 떨어진다.
- **캐스케이드** — 작은 모델에 먼저 시키고, 결과가 검사(신뢰도, 형식 검증, 테스트 통과 등)를 통과하지 못하면 큰 모델로 다시 보낸다. 판정을 결과로 하니 정확하지만, 실패한 요청은 두 번 호출한 만큼 돈과 시간이 든다.
- **에스컬레이션** — 작은 모델이 작업 전체를 진행하다가 스스로 어렵다고 판단한 지점에서만 큰 모델에 자문을 구한다. 앤트로픽 문서는 이를 executor + advisor 패턴으로 설명하고, 반대 방향인 [[오케스트레이터-워커]](큰 모델이 계획하고 작은 모델 워커에 일을 나눠주는 구조)와 함께 두 가지 대표적 다중 모델 전략으로 든다.

## 라우터를 어떻게 만드나

사전 라우팅의 핵심은 "이 요청은 작은 모델로도 충분한가"를 맞히는 분류기다. LMSYS의 오픈소스 프레임워크 RouteLLM은 강한 모델과 약한 모델 한 쌍을 두고, 사람 선호 데이터(Chatbot Arena)로 학습한 라우터가 요청마다 강한 모델이 필요한 정도를 점수로 낸다. 제공하는 라우터는 행렬 분해(`mf`, 권장), 가중 Elo(`sw_ranking`), BERT 분류기, LLM 기반 분류기 등이다.

운영에서 조절하는 값은 **임계값** 하나다.

```
라우터 점수 ≥ 임계값 ─▶ 강한 모델
라우터 점수 <  임계값 ─▶ 약한 모델

임계값 ↑  강한 모델 호출 비율 ↓  비용 ↓  품질 위험 ↑
임계값 ↓  강한 모델 호출 비율 ↑  비용 ↑  품질 안정
```

RouteLLM은 내 요청 샘플로 임계값을 보정해 "강한 모델 호출 비율 50%"처럼 목표를 맞추는 방법을 제공한다. README는 MT Bench 같은 벤치마크에서 GPT-4 성능의 95%를 유지하면서 비용을 최대 85%까지 줄였다고 밝힌다. 이 수치는 그 프로젝트가 고른 모델 쌍과 벤치마크 기준이므로 내 작업에 그대로 옮겨오면 안 된다.

## 라우팅 전에 먼저 볼 것

라우팅은 생각보다 이기기 어렵다. 앤트로픽의 다중 모델 전략 문서는 "한 모델의 점수 대 비용 곡선 전체를 이길 때만 조합을 만들라"는 원칙을 먼저 둔다.

- **같은 모델의 추론 강도(effort)를 낮추는 것이 더 나은 지렛대일 때가 많다.** 문서는 모델을 바꾸기 전에 단일 모델에서 effort를 바꿔가며 측정해보라고 하고, 대부분의 작업은 거기서 끝난다고 쓴다.
- **에스컬레이션은 작은 모델이 물어볼 때만 효과가 있다.** 앤트로픽 내부 측정에서 GPQA Diamond는 198문제 중 한 번도 자문을 부르지 않아 실행 모델 단독과 차이가 없었고, 다른 과제에서는 300개 중 1개만 자문해 오히려 단독보다 점수가 낮았다. 그래서 자문 호출 비율(consult rate)을 먼저 재보라고 한다.
- **위임은 특정 조건에서만 이겼다.** 같은 문서는 비용 꼬리가 긴 반복 작업과 한 컨텍스트 창을 넘는 작업에서만 위임 쪽이 앞섰고, 하나로 이어진 의존 작업이거나 한 컨텍스트에 들어가는 작업에서는 큰 모델 단독을 낮은 effort로 돌린 쪽이 측정한 모든 경우에 앞섰다고 밝힌다.

## 트레이드오프

- **비용의 실제 결정 요인은 작은 모델이 실패한 요청이다.** 실패한 시도도 토큰 비용은 청구되고, 캐스케이드로 재시도하면 시간도 두 배가 든다. 앤트로픽 문서의 표현대로 "청구서는 값싼 모델이 실패한 작업이 결정한다".
- **라우터 자체도 비용이다.** 분류기 호출이 추가되고, 앤트로픽의 advisor 툴은 자문을 한 번도 부르지 않아도 툴 정의만으로 요청마다 약 1,000 토큰이 붙는다고 문서에 적혀 있다.
- **캐시를 잃는다.** [[프롬프트 캐싱]]은 모델 단위로 격리되므로, 요청을 여러 모델로 흩으면 같은 앞부분을 재사용하지 못하는 만큼 절감 효과가 깎인다.
- **동작이 두 갈래가 된다.** 같은 질문에 모델에 따라 다른 문체와 다른 판단이 나온다. 사용자 경험의 일관성, 디버깅 난이도가 함께 올라간다.

## 주의사항

- **평가셋 없이 라우팅하지 않는다.** 라우팅의 이득은 "품질을 얼마나 잃고 비용을 얼마나 줄였나"라는 두 숫자로만 판단할 수 있다. [[에이전트 평가]]의 평가셋을 같은 조건으로 돌려 단일 모델의 낮은 effort, 한 단계 아래 모델 단독과 비교한다.
- **정확도도 같이 잰다.** 비용만 보면 라우팅은 늘 이겨 보인다. 앤트로픽 측정에서 작은 모델 서브에이전트를 붙인 코딩 구성은 시도당 비용이 32% 줄었지만 통과율이 약 4%포인트 떨어졌다.
- **어느 모델로 갔는지 기록한다.** 라우팅 결정과 그 근거 점수를 [[트레이싱과 관측]]에 남기지 않으면, 품질이 떨어졌을 때 라우터 탓인지 모델 탓인지 가를 수 없다.
- **섀도 운영 후 전환한다.** 새 라우팅 구성을 트래픽 일부에 그림자로 돌려 결과를 비교한 뒤 바꾼다.
- **모델이 나올 때마다 다시 잰다.** 새 모델은 모델 간 성능 격차와 가격 비율을 동시에 바꾼다. 지난 분기에 맞던 임계값이 이번 분기에는 틀릴 수 있다.

## 핵심 정리

모델 라우팅은 요청 난이도에 맞춰 모델을 골라 비용을 줄이는 설계이고, 호출 전에 예측하는 사전 라우팅, 작은 모델 결과를 검사해 넘기는 캐스케이드, 작은 모델이 필요할 때만 큰 모델을 부르는 에스컬레이션이 대표 형태다. 다만 같은 모델의 effort를 낮추는 것이 더 단순하고 강한 대안일 때가 많아서, 라우팅은 단일 모델의 비용 대 점수 곡선을 실제로 이긴다는 측정이 있을 때만 들인다. 비용을 결정하는 건 작은 모델이 실패한 요청이라는 점을 잊지 않는다.
