매 요청마다 똑같이 들어가는 앞부분을 서버에 재사용 가능한 상태로 남겨 비용과 지연을 줄이는 기능으로, 접두사 전체가 바이트 단위로 같아야만 적중하므로 프롬프트를 어떤 순서로 조립하느냐가 사실상 전부다.
기준 시점: 2026-11

## 왜 필요한가

[[에이전트 루프]]는 같은 시스템 프롬프트와 같은 툴 목록을 턴마다 다시 보낸다. 10턴이면 열 번, 100턴이면 백 번이다. 대화가 길어질수록 매 요청의 입력 토큰은 이전 대화 전체를 포함해 불어난다.

캐싱은 이 반복분을 다시 계산하지 않게 한다. 다만 **"비슷하면" 되는 게 아니라 "바이트가 같아야" 한다.** 이 한 줄에서 나머지가 전부 따라 나온다.

## 동작 원리 — 접두사 일치

캐시 키는 각 중단점(breakpoint)까지 렌더링된 프롬프트의 **정확한 바이트**에서 나온다. 중간에 한 글자만 달라져도 그 지점 이후는 전부 무효가 된다.

렌더링 순서는 고정이다.

```
tools  ──▶  system  ──▶  messages
  │           │             │
  │           │             └─ 턴마다 늘어남 (변동)
  │           └─ 고정이어야 함
  └─ 위치 0. 여기가 바뀌면 전부 무효
```

그래서 설계 원칙은 단순하다. **안정적인 것을 앞에, 변하는 것을 뒤에.**

- 절대 안 변함 → 맨 앞
- 세션마다 변함 → 전역 접두사 뒤
- 턴마다 변함 → 끝
- 요청마다 변함(타임스탬프·UUID) → 없애거나 맨 끝으로

## 캐시를 조용히 깨뜨리는 것들

에러가 안 난다. 그냥 요금이 올라간다. 이게 가장 고약한 점이다.

| 패턴 | 왜 깨지는가 |
| --- | --- |
| 시스템 프롬프트에 `datetime.now()` | 접두사가 매 요청 달라진다 |
| 앞쪽에 요청 ID·UUID | 같은 이유 |
| `json.dumps()`를 정렬 없이 | 직렬화 순서가 비결정적 |
| 시스템 프롬프트에 사용자 ID 삽입 | 사용자별 접두사가 되어 공유가 안 됨 |
| 조건부 시스템 섹션 (`if flag: system += ...`) | 플래그 조합마다 다른 접두사 |
| 사용자별로 달라지는 툴 목록 | 툴은 위치 0이라 전부 무효 |

흔한 사고 형태는 "처음부터 잘못 만든 것"이 아니라 **회귀**다. 처음엔 잘 동작하다가, 나중에 시스템 프롬프트에 동적 필드 하나가 추가되면서 조용히 전부 미스가 되고 몇 달 동안 아무도 모른다.

## 무엇이 무엇을 무효화하는가

전부 아니면 전무가 아니다. 캐시는 세 계층이고 변경은 자기 계층과 그 아래만 건드린다.

| 바꾼 것 | tools | system | messages |
| --- | :---: | :---: | :---: |
| 툴 정의 추가·삭제·순서변경 | 무효 | 무효 | 무효 |
| 모델 교체 | 무효 | 무효 | 무효 |
| 시스템 프롬프트 내용 | 유지 | 무효 | 무효 |
| `tool_choice`, 이미지 | 유지 | 유지 | 무효 |
| 메시지 내용 | 유지 | 유지 | 무효 |

읽는 법: `tool_choice`는 요청마다 바꿔도 tools+system 캐시가 살아 있다. 반대로 **툴 정의와 모델 교체만이 전면 재구축을 강제한다.** 대화 중에 "모드"를 바꾸려고 툴 목록을 갈아끼우면 캐시가 통째로 날아가므로, 모드는 메시지 내용으로 넘기는 편이 낫다.

## 비용 계산

- **쓰기**: 5분 TTL은 기본가의 1.25배, 1시간 TTL은 2배
- **읽기**: 기본 입력가의 약 0.1배 (최신 모델일수록 더 낮다)

손익분기가 TTL마다 다르다.

```
5분 TTL  : 1.25 + 0.1 = 1.35  vs  캐시 없이 2.0   → 2회면 이득
1시간 TTL: 2.0  + 0.2 = 2.2   vs  캐시 없이 3.0   → 3회는 돼야 이득
```

1시간 TTL은 트래픽이 띄엄띄엄할 때 엔트리를 살려두지만, 쓰기 비용이 두 배라 더 많은 읽기가 있어야 본전이다.

## 두 가지 함정

**최소 토큰 수를 못 넘기면 조용히 캐시되지 않는다.** 에러도 경고도 없고 `cache_creation_input_tokens`가 0으로 올 뿐이다. 더 성가신 건 **이 최솟값이 세대 순으로 단조롭지 않다**는 것이다. 최신 모델군은 512토큰이지만 일부 이전 모델은 4096토큰이다. 3천 토큰짜리 프롬프트가 어떤 모델에서는 캐시되고 어떤 모델에서는 안 된다. 쓰기 전에 그 모델의 값을 확인해야 한다.

**수명은 요청이 끝난 시점이 아니라 시작된 시점부터 센다.** 생성 시간이 수명을 깎는다는 뜻이다. 4분짜리 생성을 하면 5분 TTL에서 다음 요청이 시작할 여유는 1분뿐이다. 다만 캐시를 읽으면 추가 비용 없이 타이머가 갱신되므로, 접두사를 공유하는 요청이 5분 안쪽 간격으로 계속 들어오면 5분 TTL만으로 무기한 따뜻하게 유지된다.

## 확인하는 법

응답의 `usage`가 유일한 근거다.

| 필드 | 뜻 |
| --- | --- |
| `cache_creation_input_tokens` | 이번에 캐시에 쓴 토큰 (쓰기 프리미엄 지불) |
| `cache_read_input_tokens` | 캐시에서 읽은 토큰 (약 0.1배) |
| `input_tokens` | **캐시되지 않은 나머지만** |

전체 프롬프트 크기는 셋의 합이다. `input_tokens`만 보고 "요청이 작다"고 판단하면 안 된다.

반복 요청에서 `cache_read_input_tokens`가 계속 0이면 위의 무효화 요인 중 하나가 작동하고 있다. 어디서 깨졌는지는 **연속된 두 요청의 전체 JSON 본문을 떠서 diff**하면 나온다. 겹치는 구간 안에서 처음 갈라지는 지점이 범인이다(이때 `cache_control` 마커는 요청마다 움직이는 게 정상이므로 빼고 비교한다).

## 주의사항

- **설정할 때 한 번 확인하고 끝내지 않는다.** 프롬프트 조립 코드가 바뀔 때마다 다시 본다. 두 번째 동일 요청에서 `cache_read_input_tokens > 0`인지 검사하는 통합 테스트를 두는 게 가장 확실하다.
- **접두사가 없는데 캐싱을 켜지 않는다.** 앞부분이 요청마다 다르면 재사용할 접두사 자체가 없다. 마커만 붙이면 읽기 없이 쓰기 프리미엄만 낸다.
- **갈라져 나가는 호출은 부모의 접두사를 그대로 복사한다.** 요약·압축·서브에이전트가 별도 호출을 만들 때 `system`·`tools`·`model`을 조금이라도 다르게 재조립하면 부모 캐시를 완전히 놓친다.
- **캐시는 모델 단위로 격리된다.** 작업마다 다른 모델로 라우팅하는 설계는 캐시 재사용을 그만큼 포기하는 것이다.

## 핵심 정리

프롬프트 캐싱은 접두사 바이트 일치라는 단 하나의 규칙 위에 서 있고, 그래서 마커를 어디 붙이느냐보다 **프롬프트를 어떤 순서로 조립하느냐**가 결정적이다. 안정적인 것을 앞에 두고 변하는 것을 뒤로 미루면 대부분 저절로 되고, 시스템 프롬프트에 타임스탬프 하나를 끼워 넣으면 아무리 마커를 붙여도 되지 않는다. 실패가 조용하다는 점이 가장 위험하므로 — 에러 없이 요금만 오른다 — `usage`의 캐시 필드를 지속적으로 감시하는 장치를 함께 두어야 한다. [[컨텍스트 엔지니어링]]이 "무엇을 넣을까"의 문제라면, 캐싱은 "어떤 순서로 넣을까"의 문제다.
