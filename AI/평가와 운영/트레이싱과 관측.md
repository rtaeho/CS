에이전트는 실행마다 다른 경로를 밟고 상태를 누적하므로, 어떤 툴을 어떤 인자로 몇 번 호출했는지를 실행 시점에 남겨두지 않으면 사후에는 무엇이 잘못됐는지 복원할 방법이 없다.
기준 시점: 2026-11

## 왜 필요한가

일반 웹 서버라면 에러 로그와 스택 트레이스로 대부분 해결된다. 같은 요청을 다시 보내면 같은 일이 일어나기 때문이다.

에이전트는 그렇지 않다. [[멀티에이전트의 실패 모드]]에서 본 대로 같은 프롬프트로도 실행마다 다른 결정을 하고, 상태를 들고 있어 오류가 누적된다. 그래서 "재현해보자"가 통하지 않는다. 사용자가 "에이전트가 뻔한 정보를 못 찾는다"고 신고해도 왜 그런지 볼 수 없는 상황이 실제로 벌어진다. Anthropic도 프로덕션 트레이싱을 전면 도입하고 나서야 원인을 진단하고 체계적으로 고칠 수 있었다고 적었다.

게다가 [[에이전트 평가]]의 거의 모든 지표가 궤적 기록을 전제로 한다. 툴 호출 정확도도 인자 정확도도 호출 기록이 없으면 계산 자체가 불가능하다. **관측은 디버깅 편의가 아니라 평가의 전제 조건이다.**

## 무엇을 남기는가

한 번의 실행을 하나의 트레이스로 보고, 그 안의 각 단계를 스팬(span)으로 중첩시키는 게 기본 구조다.

```
trace: 사용자 요청 1건
└─ span: agent run                       총 12.4s / 8,200 tokens
   ├─ span: llm call #1                  1.1s / 1,400 tokens
   ├─ span: tool search_docs             0.4s   args={q:"환불 규정"}  → 3건
   ├─ span: llm call #2                  2.0s / 2,600 tokens
   ├─ span: tool get_order                0.2s   args={id:"A-991"}   → 404
   ├─ span: llm call #3                  1.8s / 2,100 tokens
   └─ span: tool get_order                0.2s   args={id:"A991"}    → OK
                                                  └ 재시도로 복구된 지점
```

이 그림에서 바로 읽히는 것들이 있다. 토큰이 어디서 쏠렸는지, 어떤 툴이 실패했는지, 모델이 인자를 고쳐 재시도했는지. 답만 보면 "정상 처리"인 실행이다.

최소한 이 정도는 남긴다.

- **툴 호출** — 이름, 인자, 반환값(또는 요약), 지연, 성공 여부
- **모델 호출** — 모델 이름과 버전, 입력·출력 토큰 수, 지연, 중단 사유
- **계층 관계** — 어느 호출이 어느 단계에서 나왔는지. 서브에이전트가 있으면 부모-자식으로 묶는다
- **식별자** — 세션·실행·사용자를 잇는 키. 신고된 실행을 찾아갈 수 없으면 기록이 있어도 못 쓴다

## 표준은 아직 움직이고 있다

OpenTelemetry가 GenAI용 시맨틱 컨벤션을 정의하고 있다. 모델 호출 스팬에 대한 규약이 먼저 자리를 잡았고, 에이전트·프레임워크 스팬에 대한 규약(`gen_ai.operation.name`을 `create_agent`로 두는 식)도 올라와 있다.

다만 **에이전트 쪽 규약은 아직 Development 상태**다. 속성 이름이 바뀔 수 있다는 뜻이고, 실제로 버전에 따라 내보내는 규약이 달라진다. 기존 계측은 기본적으로 예전 버전을 유지하고, 최신 실험 규약을 쓰려면 환경변수로 따로 opt-in 해야 한다.

실무적 함의는 단순하다. **모델 호출 스팬은 표준에 맞춰 내보내고, 에이전트 전용 속성 이름에는 코드를 강하게 묶지 않는 것이다.** 규약 버전을 먼저 확인하고 쓴다.

## 주의사항

- **민감 정보가 그대로 들어간다.** 프롬프트와 툴 반환값에는 사용자 데이터가 섞인다. Anthropic은 개별 대화 내용은 들여다보지 않고 결정 패턴과 상호작용 구조를 관측한다고 밝혔는데, 이 구분이 참고가 된다. 무엇을 남기고 무엇을 지울지 처음부터 정한다.
- **전부 남기면 비용이 는다.** 긴 프롬프트와 큰 반환값을 통째로 저장하면 저장소가 금방 찬다. 길이를 자르거나 샘플링하되, **실패한 실행은 샘플링에서 빼고 전부 남긴다.** 고칠 단서가 거기 있다.
- **집계만 보면 못 찾는다.** 평균 지연과 성공률 대시보드로는 "가끔 20번 호출하는 실행"을 못 본다. 분포와 꼬리를 보고, 개별 트레이스로 내려갈 수 있어야 한다.
- **나중에 붙이면 늦다.** 사고가 난 뒤 계측을 추가해도 그 사고의 기록은 이미 없다. 토큰·호출 횟수·실패는 처음부터 남긴다.

## 핵심 정리

에이전트는 비결정적이고 상태를 누적하므로 재현으로 디버깅할 수 없고, 실행 시점에 남긴 궤적만이 유일한 단서다. 트레이스-스팬 구조로 툴 호출의 이름·인자·반환·지연과 모델 호출의 토큰을 계층째 남기는 게 기본이고, OpenTelemetry의 GenAI 규약이 표준 자리를 잡아가는 중이되 에이전트 쪽은 아직 Development라 속성 이름에 강하게 의존하지 않는 편이 안전하다. 민감 정보와 저장 비용 때문에 전부 남길 수는 없으니, 자르고 샘플링하더라도 **실패한 실행만은 통째로 남긴다.**
