에이전트의 응답 시간을 "모델 호출 횟수 × 첫 토큰까지의 시간 + 출력 토큰 생성 시간"으로 분해하고, 스트리밍·병렬 툴 호출·호출 횟수 줄이기로 실제 지연과 사용자가 느끼는 지연을 함께 줄이는 설계다.

기준 시점: 2026-11

## 왜 필요한가

단일 LLM 호출이면 지연은 모델 하나의 속도 문제다. 에이전트는 다르다. [[에이전트 루프]]가 툴을 부를 때마다 모델 호출이 한 번씩 더 생기고, 각 호출은 다시 프롬프트를 읽고 첫 토큰을 내기까지 기다린다. 호출 3~4번짜리 작업이면 그 대기가 서너 번 쌓인다. 여기에 툴 실행 시간이 순서대로 더해진다.

그래서 "더 빠른 모델로 바꾸면 된다"는 직관이 자주 틀린다. 앤트로픽 쿡북의 측정에서 Haiku 5.5는 토큰을 가장 빨리 쓰지만 작업당 출력 토큰을 더 많이 만들어, p90 기준으로는 오히려 작업이 더 오래 걸릴 수 있었다. 어디서 기다리는지 분해하지 않고 모델만 바꾸면 엉뚱한 곳을 고치게 된다.

## 무엇을 재는가

앤트로픽 문서와 쿡북이 쓰는 지표는 셋이다.

- **TTFT(Time to First Token)** — 요청을 보낸 뒤 첫 토큰이 나올 때까지. 스트리밍 UI에서 "반응이 있다"고 느끼는 시점이다.
- **TTLT(Time to Last Token)** — 응답이 끝날 때까지 걸린 전체 시간.
- **OTPS(Output Tokens Per Second)** — 그 사이의 생성 속도.

쿡북은 작업 시간을 이렇게 근사한다.

```
TTLT ≈ 호출 수 × TTFT  +  출력 토큰 수 ÷ OTPS  +  클라이언트·서버 쪽 추가 지연
        └ 호출을 줄이면  └ 출력을 줄이거나       └ 툴 실행, 네트워크,
          여기가 준다      빠른 모드를 쓰면 준다     순차 실행 대기
```

이 식이 곧 최적화 지도다. 호출 수를 줄이는 것, 출력 토큰을 줄이는 것, 기다리는 동안 다른 일을 하는 것이 각각 다른 항을 깎는다.

평균이 아니라 **백분위수**로 본다. 쿡북은 p50과 p90을 쓰고, 전화 상담처럼 끊김이 치명적인 곳은 p90 TTFT로, 채팅 에이전트는 p50 TTLT로 판단하라고 했다. 지연은 잡음이 커서 같은 기준선의 p90 TTLT가 측정 회차마다 1.6초씩 흔들렸고, 그래서 부트스트랩 검정으로 유의한 차이만 인정했다.

## 체감 지연 줄이기 — 스트리밍

스트리밍은 전체 응답을 기다리지 않고 생성되는 대로 토큰을 보내는 방식이다. 총 시간(TTLT)은 그대로지만 사용자는 첫 토큰부터 읽기 시작하므로 기다림이 짧게 느껴진다. Claude API는 `"stream": true`를 주면 [[SSE]]로 이벤트를 흘려보낸다.

```
message_start                       빈 content를 가진 Message
├ content_block_start  [0] text
│  ├ content_block_delta  text_delta "안녕"
│  ├ content_block_delta  text_delta "하세요"
│  └ content_block_stop
├ content_block_start  [1] tool_use
│  ├ content_block_delta  input_json_delta '{"city":'
│  ├ content_block_delta  input_json_delta '"Seoul"}'
│  └ content_block_stop               ← 여기서 JSON을 파싱한다
├ message_delta                     stop_reason 등 최상위 변경
└ message_stop
   (중간중간 ping, 과부하 시 error 이벤트가 섞일 수 있다)
```

에이전트에서 스트리밍이 주는 이점은 텍스트 표시만이 아니다.

- **툴 호출을 빨리 알아챈다.** `tool_use` 블록이 닫히는 순간 툴 실행을 시작할 수 있다. 응답 전체가 끝나길 기다릴 필요가 없다.
- **중간 진행을 보여준다.** 사고(thinking)를 켜면 `thinking_delta`로 추론이 흘러나온다. "지금 무엇을 하고 있다"는 표시만으로도 체감 대기는 줄어든다.

주의할 점도 문서에 있다. 툴 인자는 **부분 JSON 문자열**로 오므로 블록이 닫힐 때까지 모아서 파싱해야 하고, API는 키와 값이 완성될 때까지 버퍼링하므로 툴 인자 생성 중에는 이벤트 사이에 공백이 생길 수 있다. 또 새로운 이벤트 타입이 추가될 수 있으니 모르는 이벤트는 무시하도록 짠다.

## 실제 지연 줄이기 — 병렬 툴 호출

Claude는 한 응답에 여러 `tool_use` 블록을 낼 수 있고 이것이 기본 동작이다. 문서는 실행 순서를 정하지 않고 호출하는 쪽에 맡긴다.

```
순차 실행                              병렬 실행
모델 ─▶ get_weather(서울)   1.2s       모델 ─┬▶ get_weather(서울)   1.2s
     ─▶ get_weather(부산)   1.1s            ├▶ get_weather(부산)   1.1s
     ─▶ get_time(서울)      0.3s            └▶ get_time(서울)      0.3s
     합계 2.6s                              가장 느린 것만 기다림 1.2s
```

병렬이 이득이 되려면 두 가지가 맞아야 한다.

- **모델이 병렬로 요청해야 한다.** 문서가 꼽은 가장 흔한 실패는 결과 형식이다. 툴 결과를 툴마다 별도의 user 메시지로 돌려주면 모델이 병렬 호출을 피하도록 "학습"된다. **모든 `tool_result`를 다음 user 메시지 하나에 모으고, 텍스트보다 앞에 둔다.**
- **실행하는 쪽이 동시에 돌려야 한다.** `Promise.all`이나 `asyncio.gather`로 돌린다. 문서는 서로 독립적인 읽기 전용 작업은 병렬이 보통 안전하고, 부작용·공유 상태·순서 의존이 있는 툴은 순차가 낫다고 쓴다. 순차로 돌리다 앞 호출이 실패해 뒤를 건너뛰더라도 건너뛴 호출에 `is_error: true`인 `tool_result`를 돌려줘야 한다.

```ts
// 병렬 실행 후 결과를 한 메시지로 모은다
const toolUses = response.content.filter((b) => b.type === "tool_use");
const results = await Promise.all(
  toolUses.map(async (call) => {
    try {
      const out = await runTool(call.name, call.input);
      return { type: "tool_result", tool_use_id: call.id, content: out };
    } catch (e) {
      return { type: "tool_result", tool_use_id: call.id, content: String(e), is_error: true };
    }
  })
);
messages.push({ role: "assistant", content: response.content });
messages.push({ role: "user", content: results }); // 텍스트 블록을 넣는다면 results 뒤에
```

순서가 필요하면 끄면 된다. `tool_choice` 안에 `disable_parallel_tool_use: true`를 두면 응답당 툴 호출이 최대 하나가 된다. 컴퓨터 사용·브라우저 사용 툴의 묶음 액션은 반대로 반드시 순서대로, 첫 실패에서 멈춰야 한다.

한 단계 더 나가면 **독립적인 하위 작업을 서브에이전트로 동시에 돌리는 방법**이 있다([[서브에이전트와 컨텍스트 격리]]). 쿡북 예시에서 Haiku 5.5 서브에이전트 셋을 나란히 돌려 6.8초가 1.5초로 줄었고, 작업 전체로는 9.5초가 5.7초가 됐다.

## 호출 수 줄이기

식의 첫 항(호출 수 × TTFT)은 모델을 몇 번 부르느냐에 비례한다. 쿡북이 효과를 확인한 방법들이다.

- **미리 가져오기(prefetch)** — 거의 매번 필요한 정보를 첫 호출 전에 넣어두면 모델이 툴로 가져오는 왕복이 사라진다. 작업당 호출이 3.5회에서 2.4회로, p50이 6.2초에서 5.3초로 줄었다.
- **툴 반환을 크게** — 페이지를 잘게 나눠 여러 번 가져오게 하지 않고 한 번에 더 많이 준다. p50이 약 10% 줄었다. [[툴 설계 원칙]]의 "적은 수의 강한 툴"과 같은 방향이다.
- **프로그램적 툴 호출** — 모델이 호출 사이마다 다시 샘플링되지 않도록, 여러 호출을 스크립트가 처리하게 한다. 46.8초가 36.0초가 됐고 출력 토큰은 5,262에서 816으로 줄었다.

## 그 밖의 지렛대

| 방법 | 깎는 항 | 쿡북 측정 | 대가 |
|---|---|---|---|
| 출력 형식 지정 | 출력 토큰 | 한 판단이 46.4초 → 4.9초 | 없음에 가깝다 |
| effort 낮추기 | 출력(사고) 토큰 | low에서 p50 ×0.87 | 정확도 하락 가능 |
| 빠른 모드 | OTPS | p50·p90 53~59% 감소 | 토큰 단가 약 2배 |
| [[프롬프트 캐싱]] | 긴 프롬프트의 TTFT | 짧은 작업은 유의차 없음, 146K 토큰 프롬프트 2턴째 1.7초 → 0.5초 | 캐시 무효화 관리 |
| 백그라운드 [[컨텍스트 압축]] | 압축 순간의 대기 | 최장 대기 21.4초 → 4.9초 | 그 사이 프롬프트가 더 크다 |
| 작은 모델 ([[모델 라우팅]]) | TTFT·OTPS | 정확도·지연이 가격만큼 따라오지 않음 | 정확도 |

effort 조절은 별도 주제([[Effort 설정]])이고, 여기서는 "사고 토큰도 출력 토큰이라 지연에 그대로 들어간다"는 점만 기억하면 된다.

프롬프트 길이 자체의 영향은 생각보다 작았다. 쿡북에서 입력을 약 17K에서 200K 토큰으로 늘리자 TTFT가 약 0.5초, 대략 10만 토큰당 0.25초 늘었다. 지연을 크게 좌우하는 건 입력보다 **출력 토큰과 호출 횟수**다.

## 트레이드오프

- **속도를 내는 지렛대 대부분은 추론을 줄인다.** effort 낮추기, 작은 모델, 사고 끄기가 그렇다. 쿡북에서 Haiku 5.5의 사고를 끄자 정확도가 97.5%에서 73.5%로 떨어졌다. 모든 변경은 정확도 하한(쿡북은 95%)과 함께 잰다.
- **돈으로 사는 속도가 있다.** 빠른 모드는 지연을 절반 넘게 줄였지만 작업당 비용이 두 배 가까이 됐다. 반대로 프롬프트 캐싱은 비용을 85% 줄였지만 짧은 작업의 지연은 바꾸지 못했다. 비용 최적화와 지연 최적화는 다른 문제다.
- **병렬은 비용을 줄이지 않는다.** 같은 일을 동시에 할 뿐이라 토큰은 그대로이고, 긴 컨텍스트를 공유하는 서브에이전트는 미리 캐시를 데워두거나 시작을 엇갈리게 하지 않으면 각자 캐시 없이 읽는다.

## 주의사항

- **품질부터 맞추고 지연을 줄인다.** 앤트로픽 문서는 제약 없이 잘 동작하는 프롬프트를 먼저 만든 뒤 지연을 줄이라고 한다. 너무 일찍 줄이면 최고 성능이 어디인지 알 수 없다.
- **한 번에 하나씩 바꾼다.** 여러 지렛대를 동시에 바꾸면 무엇이 효과였는지 가를 수 없다. 기준선을 정하고 [[에이전트 평가]]의 평가셋으로 하나씩 적용한다.
- **캐시를 깨는 것을 조심한다.** 시스템 프롬프트 앞부분의 타임스탬프나 요청 ID, 툴·모델·effort 변경은 캐시를 무효화해 TTFT를 되돌린다.
- **`max_tokens`를 너무 낮추지 않는다.** 사고와 툴 호출도 이 한도에 포함되므로, 낮게 잡으면 답이 나오기 전에 끊길 수 있다.
- **어디서 기다렸는지 기록한다.** 호출별 TTFT, 출력 토큰, 툴 실행 시간을 [[트레이싱과 관측]]에 남겨야 식의 어느 항이 문제인지 보인다.

## 핵심 정리

에이전트의 지연은 "호출 수 × TTFT + 출력 토큰 ÷ 생성 속도 + 툴·네트워크 대기"로 분해된다. 스트리밍은 총 시간은 그대로 두고 체감 지연을 줄이며, 병렬 툴 호출과 서브에이전트는 독립 작업을 동시에 돌려 실제 지연을 줄이고, 미리 가져오기·큰 툴 반환·프로그램적 툴 호출은 호출 수 자체를 줄인다. 병렬 호출을 유지하려면 모든 툴 결과를 한 user 메시지에 모아야 한다. 속도를 내는 지렛대 대부분은 추론이나 돈을 대가로 하므로, 백분위수 지연과 정확도를 함께 재며 하나씩 적용한다.
