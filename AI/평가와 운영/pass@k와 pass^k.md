pass@k는 같은 과제를 k번 시도해 최소 한 번 성공할 확률이고, pass^k는 k번 모두 성공할 확률로, 비결정적인 에이전트를 "한 번은 해내는가"와 "매번 해내는가" 중 어느 쪽으로 잴지 가르는 두 지표다.

기준 시점: 2026-11

## 왜 필요한가

LLM 에이전트는 같은 입력에도 매번 다른 궤적을 밟는다. 앤트로픽의 에이전트 평가 글은 이 점을 "한 평가 실행에서 통과한 과제가 다음 실행에서는 실패할 수 있다"고 표현하고, 그래서 과제마다 여러 번(trial) 돌려야 한다고 설명한다.

여러 번 돌리고 나면 결과를 하나의 숫자로 묶어야 하는데, 묶는 방법에 따라 같은 에이전트가 정반대로 보인다.

```
과제 1개, 10번 실행 → 성공 7번, 실패 3번

"한 번이라도 성공했나?"   → 예     → 이 과제는 풀 수 있다
"매번 성공했나?"         → 아니오  → 이 과제는 믿고 맡길 수 없다
"평균 성공률은?"          → 70%
```

세 답이 모두 맞다. 문제는 제품이 어떤 질문을 해야 하는가다. 코드 후보를 여러 개 뽑아 테스트로 걸러 쓰는 도구라면 "한 번이라도"가 맞는 질문이고, 고객 환불을 처리하는 상담 에이전트라면 "매번"이 맞는 질문이다. 질문을 정하지 않고 평균만 보면 [[에이전트 평가]] 결과가 실제 사용 경험과 어긋난다.

## 정의

과제 하나에서 한 번 시도의 성공 확률을 p라 하고, 시도끼리 독립이라고 두면 다음과 같다.

```
pass@1 = p                     (첫 시도에 성공할 확률)
pass@k = 1 − (1 − p)^k         (k번 중 최소 1번 성공 = 1 − 전부 실패할 확률)
pass^k = p^k                   (k번 모두 성공)
```

앤트로픽 글의 정의도 같다. pass@k는 "k번 시도 중 최소 한 번 올바른 해를 얻을 가능성", pass^k는 "k번의 trial이 모두 성공할 확률"이다. 평가 세트 전체 점수는 과제별 값을 구한 뒤 과제 수로 평균 낸다.

### k가 커질수록 두 지표는 반대로 간다

p = 0.75인 과제로 계산하면 다음과 같다.

```
 k   │ pass@k  │ pass^k
─────┼─────────┼────────
 1   │ 75.0%   │ 75.0%     ← k=1에서는 둘이 같다
 3   │ 98.4%   │ 42.2%
 5   │ 99.9%   │ 23.7%
10   │ ≈100%   │  5.6%

pass@k  ──────────────────▶ 100%로 수렴 (기회가 많을수록 쉬워진다)
pass^k  ──────────────────▶   0%로 수렴 (일관성 요구가 커질수록 어려워진다)
```

앤트로픽 글이 드는 예(시도당 75%, 3번 모두 통과할 확률 약 42%)가 위 표의 k=3 줄이다. 글은 k=10쯤 되면 "pass@k는 100%에 가까워지고 pass^k는 0%로 떨어져 정반대 이야기를 한다"고 정리한다.

## 어느 쪽을 쓸까

앤트로픽 글의 기준은 "하나만 성공하면 되는 도구에는 pass@k, 일관성이 핵심인 에이전트에는 pass^k"다.

```
                 한 번 성공이면 충분한가?
                         │
          ┌──── 예 ──────┴────── 아니오 ────┐
          ▼                                 ▼
   결과를 고르는 검증 장치가 있는가?     사용자가 매번 같은 품질을 기대하는가?
          │                                 │
     예 ──┴── 아니오                     예 ──┴── 아니오
     ▼          ▼                        ▼          ▼
  pass@k     pass@1                   pass^k     pass@1
 (후보 여러 개  (사람이 첫 결과를        (고객 상담,   (평균 성공률이면
  → 테스트로    그대로 받는다)           결제·환불)    충분)
  하나 고름)
```

- **pass@k가 맞는 곳**: 후보를 여러 개 만들고 자동 검증(테스트, 컴파일, 정답 비교)으로 하나를 고를 수 있을 때. 검증기가 없으면 k개 중 어느 것이 맞는지 모르므로 pass@k는 실제로 얻는 성능이 아니다.
- **pass@1이 맞는 곳**: 사람이 첫 결과를 그대로 받는 경우. 앤트로픽 글도 코딩에서는 보통 첫 시도에 해를 찾는 것(pass@1)에 가장 관심이 있다고 적는다.
- **pass^k가 맞는 곳**: 같은 종류의 요청을 반복해서 받는 고객 대상 에이전트. 하루 1,000건을 처리하는데 과제당 성공률이 90%라면 매일 100건 가까이 사고가 난다. 앤트로픽 글은 이 지표가 "사용자가 매번 믿을 수 있는 동작을 기대하는 고객 대상 에이전트"에서 특히 중요하다고 쓴다.

## 실제로 계산하기

### 독립 가정 공식은 n번 돌린 결과로 바로 쓰기 어렵다

현실에서는 p를 모르고, 과제마다 n번 돌린 결과(성공 c번)만 있다. 가장 단순한 방법은 p̂ = c/n을 공식에 넣는 것이지만, 이 방식은 표본이 적을 때 치우친다. 대신 "n번 결과에서 k개를 비복원으로 뽑았을 때"로 세는 추정식이 널리 쓰인다.

```
pass@k 추정 = 1 − C(n−c, k) / C(n, k)     k개를 뽑았는데 전부 실패일 확률을 뺀다
pass^k 추정 =     C(c, k)   / C(n, k)     k개를 뽑았는데 전부 성공일 확률
(C는 조합 수, k ≤ n)
```

pass@k 쪽 식은 OpenAI의 Codex 논문(HumanEval, 2021)이 편향 없는 추정량으로 제안한 것으로 알려져 있고, pass^k 쪽 식은 고객 상담 에이전트 벤치마크 τ-bench가 일관성을 재려고 쓴 방식으로 알려져 있다. 두 논문 원문은 이번 실행 환경에서 받아오지 못했으니, 식 자체는 위의 조합 계산으로 직접 확인할 수 있는 범위에서만 적었다.

n = 10, c = 7이면 다음과 같다.

```
 k │ pass@k 추정 │ pass^k 추정
───┼────────────┼────────────
 1 │ 70.0%      │ 70.0%
 3 │ 99.2%      │ 29.2%
 5 │ 100%       │  8.3%      ← 실패가 3번뿐이라 5개를 뽑으면 성공이 반드시 섞인다
```

### 구현

```python
from math import comb

def pass_at_k(n: int, c: int, k: int) -> float:
    """n번 중 c번 성공. k개를 뽑았을 때 최소 1개 성공할 확률."""
    if n - c < k:          # 실패가 k개보다 적으면 반드시 성공이 섞인다
        return 1.0
    return 1.0 - comb(n - c, k) / comb(n, k)

def pass_hat_k(n: int, c: int, k: int) -> float:
    """n번 중 c번 성공. k개를 뽑았을 때 전부 성공할 확률."""
    if c < k:
        return 0.0
    return comb(c, k) / comb(n, k)

def suite_score(results: list[tuple[int, int]], k: int, metric) -> float:
    """과제별 (n, c) 목록 → 과제별로 계산한 뒤 평균."""
    return sum(metric(n, c, k) for n, c in results) / len(results)

results = [(10, 10), (10, 7), (10, 2)]          # 과제 3개
print(suite_score(results, 3, pass_at_k))       # ≈ 0.84
print(suite_score(results, 3, pass_hat_k))      # ≈ 0.43
```

## 주의사항

- **과제별로 계산한 뒤 평균 낸다.** 전체 평균 성공률을 먼저 구하고 k제곱하면 틀린다. 성공률 100%와 50%인 과제 둘의 pass^3은 (1 + 0.125) / 2 ≈ 56%인데, 평균 75%를 먼저 내고 세제곱하면 42%가 나온다. 성공률이 과제마다 고르지 않을수록 차이가 커진다.
- **k보다 n을 크게 잡는다.** n = k로 돌리면 추정이 거칠다. 비용 때문에 n을 늘리기 어렵다면, 보고하는 k를 작게 둔다.
- **독립이 아니면 숫자가 부풀거나 줄어든다.** 같은 시드, 같은 캐시, 앞 trial이 남긴 파일 같은 공유 상태가 있으면 시도끼리 상관이 생긴다. 앤트로픽 글이 trial마다 깨끗한 환경에서 격리해 돌리라고 하는 이유 중 하나다.
- **pass@k는 검증 비용을 숨긴다.** k개 후보를 만들고 고르는 데 드는 토큰·시간·검증기 비용이 지표에 안 나온다. pass@k 점수를 낼 때는 그 k를 실제 운영에서도 감당할 수 있는지 같이 적는다.
- **k와 n을 함께 보고한다.** "pass^k 40%"만 있으면 k=2인지 k=8인지 알 수 없어 비교가 불가능하다.
- **채점기 자체가 흔들리면 둘 다 의미가 없다.** [[LLM-as-judge]]처럼 채점기도 비결정적이면, 에이전트의 변동과 채점기의 변동이 섞인다. 채점기 쪽 일관성부터 따로 확인한다.

## 트레이드오프

- **비용**: 두 지표 모두 과제당 n번 실행이 필요하다. 평가 비용이 n배가 되고, 긴 에이전트 과제라면 시간도 n배다. [[프롬프트 캐싱]]이 평가 비용을 일부 줄여주지만, 캐시가 시도 사이에 상태를 공유하게 만들지 않는지는 따로 봐야 한다.
- **해상도**: pass^k는 k가 클수록 엄격해져 좋은 에이전트끼리도 차이가 크게 벌어진다. 반대로 pass@k는 k가 클수록 다들 100%에 붙어 구분이 안 된다(포화).
- **해석**: 평균 성공률 하나보다 두 숫자를 같이 볼 때 정보가 많다. pass@k는 높고 pass^k는 낮으면 "능력은 있는데 불안정하다"는 뜻이고, 이때는 모델 교체보다 프롬프트·툴 설명·가드 단계로 변동을 줄이는 쪽이 효과가 클 수 있다.

## 핵심 정리

- pass@k = k번 중 최소 1번 성공, pass^k = k번 모두 성공. k=1에서는 둘 다 시도당 성공률과 같다.
- k가 커지면 pass@k는 100%로, pass^k는 0%로 간다. 시도당 75%면 3번 모두 성공은 약 42%다.
- 검증기로 후보를 고를 수 있는 도구에는 pass@k, 매번 믿고 맡겨야 하는 고객 대상 에이전트에는 pass^k를 쓴다.
- 과제마다 n번 돌려 조합 기반 추정식으로 계산하고, 과제별로 구한 뒤 평균 낸다. k와 n을 함께 보고한다.
