Effort 설정은 같은 모델을 부르면서 요청마다 "얼마나 공들여 답할지"를 low부터 max까지 골라, 토큰 사용량(비용·지연)과 결과의 철저함을 맞바꾸는 옵션이다.

기준 시점: 2026-11

## 왜 필요한가

에이전트가 부르는 모델 호출은 난이도가 제각각이다. 툴 결과를 한 줄로 정리하는 단계와 동시성 버그의 원인을 추론하는 단계가 같은 루프 안에 섞여 있다. 모든 호출을 최대한 생각하게 두면 쉬운 단계에서도 사고 토큰이 쌓여 비용과 [[지연 시간 설계|지연]]이 늘고, 반대로 전부 짧게 답하게 하면 어려운 단계에서 실패한다.

이 문제의 전통적인 답은 [[모델 라우팅]], 즉 쉬운 요청을 작은 모델로 보내는 것이었다. 하지만 라우팅은 모델이 둘 이상 필요하고, 라우터를 따로 만들고 평가해야 하며, 모델마다 프롬프트 습관이 달라 관리할 것이 늘어난다. Effort는 **모델은 하나로 두고 "공들이는 정도"만 다이얼로 돌리는** 더 단순한 지렛대다. 앤트로픽 비용 최적화 문서도 모델을 바꾸기 전에 단일 모델의 effort부터 바꿔가며 재보라고 권한다.

## 구조

```
              같은 모델, 같은 프롬프트
                       │
          output_config.effort = ?
   ┌──────┬──────────┼──────────┬──────────┐
  low   medium      high       xhigh       max
   │                                         │
   ▼                                         ▼
 사고 적음·건너뜀                         사고 길고 잦음
 툴 호출 적고 묶어서                      툴 호출 많고 계획 설명
 짧은 확인 메시지                         자세한 요약
 ── 토큰·지연·비용 ↓ ──────────────── 토큰·지연·비용 ↑ ──
```

앤트로픽 API 기준으로 정리하면 다음과 같다.

- **요청에 한 필드로 건다.** Messages API에서는 `output_config.effort`에, Managed Agents에서는 에이전트의 모델 객체(또는 세션의 모델 오버라이드)에 `effort`를 둔다. 값을 안 주면 모델의 기본값이 적용되고, 기본값을 명시한 것과 생략한 것은 완전히 같은 동작이라고 문서는 밝힌다.
- **단계는 `low` · `medium` · `high` · `xhigh` · `max` 다섯이다.** 문서의 설명은 대략 이렇다.

| 단계 | 문서의 설명 | 전형적인 쓰임 |
| --- | --- | --- |
| `low` | 가장 효율적, 토큰을 크게 아끼는 대신 능력이 조금 줄어든다 | 서브에이전트처럼 속도·비용이 중요한 단순 작업 |
| `medium` | 균형 잡힌 절약 | 속도·비용·성능의 균형이 필요한 에이전트 작업 |
| `high` | 좋은 결과에 필요한 만큼 토큰을 쓴다 | 복잡한 추론, 어려운 코딩, 에이전트 작업 |
| `xhigh` | 장기 작업용 확장 능력 | 30분이 넘고 토큰 예산이 수백만인 코딩·에이전트 작업 |
| `max` | 토큰 제약 없는 최대 능력 | 가장 깊은 추론이 필요한 작업 |

- **기본값은 모델마다 다르다.** 대부분은 `high`가 기본인데, Claude Opus 5.5와 Haiku 5.5는 `medium`이 기본이다. 그래서 Opus 5에서 Opus 5.5로 옮기면서 effort를 생략한 요청은 한 단계 낮게 돈다. 모든 모델이 다섯 단계를 다 지원하는 것도 아니어서, `max`는 되는데 `xhigh`는 없는 모델도 있다.
- **사고뿐 아니라 모든 출력 토큰에 걸린다.** 텍스트 답변, 툴 호출과 그 인자, (켜져 있다면) 사고가 전부 대상이다. 그래서 사고를 끈 상태에서도 효과가 있다.
- **엄격한 예산이 아니라 행동 신호다.** 낮은 effort에서도 충분히 어려운 문제에는 생각을 하되, 같은 문제를 높은 effort에서보다 덜 생각한다. 정확한 토큰 상한은 여전히 `max_tokens`이고, 이 값은 사고와 답변을 합친 전체 출력의 하드 리밋이다.

### 사고(thinking)와의 관계

`thinking`은 "답하기 전에 사고 블록을 쓸지"를 정하는 **모드**이고, `effort`는 "응답 전체에 얼마나 공들일지"를 정하는 **강도**다. 둘은 다른 축이라 `adaptive`를 effort 값으로 넣으면 안 된다. 모델이 사고 여부와 깊이를 스스로 정하는 adaptive thinking 모드에서는 effort가 사실상 사고 깊이를 조절하는 주된 손잡이가 된다. 문서는 adaptive thinking이 가능한 곳에서는 effort로 사고 깊이를 조절하라고 권한다.

일부 모델은 높은 단계에서 사고를 끌 수 없다. 예를 들어 Haiku 5.5는 `high` 이하에서만 `thinking: {"type": "disabled"}`를 허용하고 `xhigh`·`max`에서는 400 오류를 돌려준다. Opus 5.5는 adaptive thinking이 항상 켜져 있어 어느 단계에서든 끌 수 없다.

### 툴 사용과의 관계

에이전트에서 effort가 눈에 띄게 드러나는 곳은 [[함수 호출|툴 호출]]이다. 문서에 따르면 낮은 effort는 여러 작업을 적은 툴 호출로 묶고, 설명 없이 바로 행동하고, 완료 후 짧게 확인한다. 높은 effort는 툴을 더 많이 부르고, 행동 전에 계획을 설명하고, 변경 사항을 자세히 요약한다. [[에이전트 루프]]에서 툴 결과만 처리하는 후속 요청은 어느 단계에서든 사고를 건너뛸 수 있다.

## 구현

요청 하나에 effort를 거는 것은 한 줄이다. 에이전트에서는 단계의 성격에 따라 다르게 거는 쪽이 실용적이다.

```python
import anthropic

client = anthropic.Anthropic()

def call(messages, effort: str, max_tokens: int):
    return client.messages.create(
        model="claude-opus-5-5",
        max_tokens=max_tokens,           # 사고 + 답변 전체의 하드 리밋
        messages=messages,
        output_config={"effort": effort},
    )

# 메인 에이전트: 판단이 필요한 계획 단계
plan = call(plan_messages, effort="high", max_tokens=32_000)

# 서브에이전트: 파일 요약처럼 단순·대량인 단계
summaries = [call(m, effort="low", max_tokens=2_000) for m in chunk_messages]
```

[[서브에이전트와 컨텍스트 격리]]처럼 상위·하위 호출이 나뉘어 있으면, 하위의 단순 탐색은 `low`, 상위의 종합 판단은 `high` 이상으로 두는 식으로 자연스럽게 갈린다.

## 트레이드오프

- **비용·지연 ↔ 능력.** effort를 낮추면 사고와 툴 호출이 줄어 토큰과 지연이 같이 준다. 사고 토큰도 출력 토큰이라 생성 시간에 그대로 들어가기 때문이다. 대신 어려운 단계에서 검색을 건너뛰거나 일찍 멈출 수 있다. 문서는 Haiku 5.5가 긴 에이전트 프롬프트에서 `low`일 때 검색을 건너뛰거나, 일찍 멈추거나, 확인을 빼먹을 가능성이 커진다고 적고 있다.
- **높을수록 좋은 것은 아니다.** 문서는 Fable 5.2 기준으로 능력 향상의 대부분이 이미 `high`에서 나오고, 그 위의 향상은 작업마다 고르지 않다고 한다. `max`는 `xhigh`보다 느리고 비싸면서도 얻는 것이 작을 때가 많고, 구조화 출력처럼 지능이 덜 필요한 작업에서는 과하게 생각할(overthinking) 수 있다는 언급도 있다.
- **라우팅과의 비교.** 모델 하나로 effort만 바꾸면 프롬프트·평가·운영 대상이 하나로 유지된다. 반대로 effort를 아무리 낮춰도 작은 모델의 단가보다 싸지지 않는 구간이 있어서, 단순·대량 작업은 [[모델 라우팅]]이 여전히 유리할 수 있다. 둘 중 무엇이 나은지는 같은 평가셋에서 비용 대 점수를 재봐야 안다.

## 주의사항

- **명시적으로 건다.** 기본값이 모델마다 달라 모델을 바꾸면 effort가 조용히 바뀐다. 문서도 첫 번째 모범 사례로 "effort를 명시적으로 설정하라"를 든다.
- **이전 모델의 설정을 그대로 옮기지 않는다.** 같은 이름의 단계라도 모델마다 보정이 달라, 예컨대 Sonnet 5.5의 `high`는 Sonnet 5의 `high`와 같은 양의 사고를 하지 않는다. 모델을 바꿀 때마다 [[에이전트 평가]]의 평가셋으로 단계별 스윕을 다시 돌린다.
- **높은 단계에서는 `max_tokens`를 넉넉히.** effort를 올려도 `max_tokens`가 작으면 사고 도중에 출력이 잘린다. 문서는 Opus 계열의 `xhigh`·`max`에서 64k 토큰부터 시작해 조정하라고 하고, Sonnet 5.5의 에이전트 코딩에는 최대치인 128,000을 쓰고 스트리밍하라고 한다.
- **답변 길이는 effort로 조절하지 않는다.** effort는 사고량을 바꿀 뿐 보이는 답의 길이는 잘 바뀌지 않는다고 문서는 여러 모델에 걸쳐 밝힌다. 길이와 말투는 프롬프트로 정한다.
- **대화 중간에 최상위 effort를 바꾸면 캐시가 깨질 수 있다.** 최상위 `output_config.effort`는 렌더링되는 프롬프트에 영향을 줘서, 요청 사이에 바꾸면 앞선 턴의 [[프롬프트 캐싱|캐시된 앞부분]]이 무효가 될 수 있다. 지원하는 모델에서는 `messages` 안에 메시지 단위 effort를 넣으면 캐시를 유지한 채 단계를 바꿀 수 있다. 그렇지 않다면 캐시에 기대는 긴 세션에서는 처음 정한 단계를 유지하고, effort는 대화 안이 아니라 작업 종류별로 나눈다.
- **낮은 effort에서 얕게 추론하면 프롬프트로 덮지 말고 단계를 올린다.** 문서는 Opus 4.7에 대해 이렇게 권하면서, 지연 때문에 낮게 유지해야 한다면 "여러 단계의 추론이 필요하니 신중히 생각하라" 같은 지시를 덧붙이라고 한다.

## 핵심 정리

Effort는 모델을 바꾸지 않고 요청마다 공들이는 정도를 `low`~`max`로 고르는 옵션이고, 사고뿐 아니라 텍스트와 툴 호출을 포함한 모든 출력 토큰에 영향을 준다. 엄격한 예산이 아닌 행동 신호이며, 상한은 여전히 `max_tokens`가 정한다. 기본값과 단계별 보정이 모델마다 달라서 명시적으로 걸고, 모델을 바꿀 때마다 평가셋으로 다시 재야 한다. 비용을 줄이려 할 때 [[모델 라우팅]]보다 먼저 시도해볼 만한 가장 단순한 지렛대다.
