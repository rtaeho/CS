이벤트 인박스는 웹훅·스케줄·백그라운드 작업 같은 외부 신호가 에이전트를 직접 깨우지 않고 내구성 있는 목록(보통 DB 테이블)에 먼저 쌓이게 해, 에이전트가 거기서 이벤트를 꺼내 처리하도록 만드는 구조다.

기준 시점: 2026-11

## 왜 필요한가

사람이 말을 걸 때만 도는 챗봇은 "요청 하나 → 런 하나"로 끝난다. 그런데 메일 도착, 결제 실패 웹훅, 매일 아침 스케줄처럼 바깥에서 신호가 들어와 에이전트가 스스로 움직여야 하면, 신호를 받자마자 런을 바로 띄우는 방식이 금방 무너진다.

```
웹훅 A ──▶ 런 1 시작 ─┐
웹훅 B ──▶ 런 2 시작 ─┼─▶ 같은 메모리·같은 대화를 동시에 읽고 쓴다
스케줄 ──▶ 런 3 시작 ─┘     → 일을 두 번 하거나 서로 덮어쓴다

런 2 도중 워커 프로세스가 죽음
  → 웹훅 B는 이미 200 OK로 응답했으니 보낸 쪽은 재전송하지 않는다
  → 이벤트 B는 어디에도 남지 않고 사라진다
```

문제는 두 가지다. 동시에 들어온 신호가 **경합하는 런**을 만들고, 런이 처리 도중 죽으면 **이벤트가 유실**된다. 앤트로픽의 항시 작동(always-on) 에이전트 가이드는 이 둘을 막는 첫 번째 구성 요소로 이벤트 인박스를 든다.

## 구조

```
 [웹훅]   [스케줄러]   [백그라운드 작업]   [사용자 응답]
    │          │              │                 │
    └──────────┴──── append ──┴─────────────────┘
                        ▼
          ┌──────────────────────────────┐
          │  inbox 테이블 (진실의 원천)    │
          │  id | source_id | status | …  │
          │  1  | gh-991    | done        │
          │  2  | mail-17   | pending     │
          │  3  | mail-18   | pending     │
          └──────────────────────────────┘
                        │ 깨우기
                        ▼
          워커(인박스당 하나만 활성)
            1. pending 이벤트를 모아서 꺼낸다 (배치)
            2. 런 실행: 메모리 읽기 → 행동 → 메모리 갱신
            3. 처리한 이벤트를 done으로 표시
```

가이드가 설명하는 원칙을 하나씩 보면 이렇다.

- **내구성 있는 목록이다.** 인박스는 "보통 데이터베이스 테이블인 내구성 있는 이벤트 목록"이고, 이벤트마다 새 행으로 덧붙이기 때문에 관계형 DB가 잘 맞는다고 한다. 각 이벤트의 상태를 추적해야 한다.
- **빠르게 확인응답한다.** 신호를 보내는 쪽 중에는 느린 응답을 실패로 보는 곳이 있다. 그래서 핸들러는 행을 적재하고 바로 응답하고, 무거운 일은 런에서 한다. 프롬프트 인젝션 검사 같은 심화 검증도 받는 순간이 아니라 런 도중에 한다.
- **인박스가 진실의 원천이다.** 워커는 깨어나면 먼저 인박스에서 대기 중인 이벤트를 꺼낸다. 이벤트 상태가 인박스에 남아 있으니 워커가 런 도중 죽어도 새 워커가 같은 이벤트를 다시 집어 재시도할 수 있다.
- **인박스당 활성 워커는 하나다.** 런끼리 일을 중복하거나 서로 덮어쓰는 것을 막는다. 런 도중 새 이벤트가 들어오면 다음 런으로 미루거나, 지금 런에 합치거나, 중단하고 다시 시작하는 세 가지 중에서 고른다.
- **모아서 처리한다.** 사용자가 짧은 메시지를 연달아 보내면 이를 묶어 에이전트가 한 번만 답하게 한다.
- **중복을 제거한다.** 출처가 주는 고유 식별자(웹훅 이벤트 ID 등)로 같은 이벤트를 걸러낸다.

인박스는 다른 구성 요소의 합류 지점이기도 하다. 가이드에 따르면 타이머는 런을 직접 시작하지 않는다. 스케줄러가 타이머 저장소를 폴링해 기한이 된 타이머를 인박스에 이벤트로 넣고 워커를 깨울 뿐이다. 그래서 인박스에는 "지금 처리할 준비가 된 이벤트만" 들어 있어야 한다. 사람의 승인을 기다리는 지연된 툴 호출도 사용자 응답이 인박스 이벤트로 돌아오면 새 런이 저장된 세션을 재개하는 방식이라, 기다리는 동안 워커는 다른 이벤트를 처리할 수 있다.

## 구현

PostgreSQL을 쓴다고 가정한 최소 골격이다. 중복 제거는 출처 ID의 유니크 제약으로, "인박스당 워커 하나"는 인박스 단위 잠금으로 건다.

```python
import json

# 적재: 핸들러는 행만 넣고 바로 응답한다
INSERT_SQL = """
INSERT INTO inbox (inbox_key, source_id, payload, status)
VALUES (%s, %s, %s, 'pending')
ON CONFLICT (inbox_key, source_id) DO NOTHING
"""

def handle_webhook(conn, inbox_key: str, event: dict) -> int:
    with conn.cursor() as cur:
        cur.execute(INSERT_SQL, (inbox_key, event["id"], json.dumps(event)))
    conn.commit()
    wake_worker(inbox_key)   # 큐 메시지나 알림만 보낸다
    return 200               # 심화 검사는 런에서 한다


# 처리: 인박스 단위 잠금을 잡은 워커 하나만 진행한다
def run_once(conn, inbox_key: str) -> None:
    with conn.cursor() as cur:
        cur.execute("SELECT pg_try_advisory_lock(hashtext(%s))", (inbox_key,))
        if not cur.fetchone()[0]:
            return           # 다른 워커가 이미 돌고 있다

        try:
            cur.execute(
                "SELECT id, payload FROM inbox "
                "WHERE inbox_key = %s AND status = 'pending' ORDER BY id",
                (inbox_key,),
            )
            batch = cur.fetchall()
            if not batch:
                return

            run_agent(inbox_key, [json.loads(p) for _, p in batch])  # 배치를 한 런으로

            cur.execute(
                "UPDATE inbox SET status = 'done' WHERE id = ANY(%s)",
                ([row_id for row_id, _ in batch],),
            )
            conn.commit()
        finally:
            cur.execute("SELECT pg_advisory_unlock(hashtext(%s))", (inbox_key,))
```

`run_agent`가 끝난 뒤에야 `done`으로 바꾸므로, 런 도중 워커가 죽으면 이벤트는 `pending`으로 남아 다음 워커가 다시 집는다. 대신 같은 이벤트가 두 번 처리될 수 있으니 런 안의 행동(메일 발송, 결제 등)은 [[멱등성]]을 갖추거나 발신함 쪽에서 한 번 더 중복을 걸러야 한다. 여러 서버에 걸친 잠금이 필요하면 [[Redis 분산 락]] 같은 방식으로 바꿀 수 있다.

## 트레이드오프

- **지연이 생긴다.** 신호 → 적재 → 깨우기 → 꺼내기를 거치므로 바로 런을 띄우는 것보다 느리다. 배치까지 하면 첫 이벤트는 일부러 조금 더 기다리게 된다.
- **처리량이 인박스 단위로 묶인다.** 인박스당 워커가 하나라서 한 사용자·한 대화에 이벤트가 몰리면 줄을 선다. 병렬성은 인박스를 어떤 단위(사용자, 대화, 작업)로 나누느냐로 조절한다.
- **"최소 한 번" 처리가 기본이 된다.** 재시도로 유실은 막지만 중복 처리 가능성을 받아들여야 한다. 그래서 출처 ID 기반 중복 제거와 행동의 멱등성이 함께 필요하다.
- **저장소가 하나 더 생긴다.** 처리 끝난 이벤트를 언제 지울지, 실패를 몇 번까지 재시도할지 같은 운영 규칙을 정해야 한다.

## 주의사항

- **확인응답 전에 검사하지 않는다.** 받는 순간 LLM 분류기나 외부 API를 부르면 보낸 쪽 타임아웃에 걸려 재전송 폭주가 난다. 핸들러에서는 서명 검증 정도만 하고 나머지는 런으로 넘긴다.
- **적재와 깨우기를 따로 실패하게 두지 않는다.** 행은 넣었는데 깨우기 신호가 빠지면 이벤트가 다음 신호가 올 때까지 잠든다. 주기적으로 `pending`을 훑는 보조 스캔을 두거나, DB 커밋과 메시지 발행을 함께 보장하는 [[Outbox 패턴]]을 쓴다.
- **런 도중 들어온 이벤트 정책을 정해 둔다.** 다음 런으로 미룰지, 지금 런에 합칠지, 끊고 다시 시작할지 정하지 않으면 사용자가 정정 메시지를 보냈는데 에이전트가 옛 지시대로 끝까지 가는 일이 생긴다.
- **인박스에 미래 이벤트를 넣지 않는다.** "내일 9시에 다시 확인" 같은 일은 타이머 저장소에 두고, 기한이 되면 그때 인박스에 넣는다. 인박스는 지금 처리할 일만 담아야 워커가 "꺼낸 건 전부 처리한다"는 단순한 규칙으로 돈다.
- **외부 내용은 런에서 의심한다.** 웹훅 본문이나 메일 내용은 남이 쓴 텍스트다. 런 안에서 프롬프트 인젝션 검사를 거친 뒤에 [[에이전트 루프]]에 넣는다.

## 핵심 정리

- 외부 신호를 에이전트에 바로 꽂지 않고, 내구성 있는 테이블에 먼저 쌓은 뒤 워커가 꺼내 처리한다.
- 핸들러는 적재 후 빠르게 응답하고, 인젝션 검사 같은 무거운 검증은 런에서 한다.
- 인박스를 진실의 원천으로 두면 워커가 죽어도 재시도할 수 있고, 인박스당 워커 하나로 경합을 막는다.
- 연달아 온 이벤트는 배치로 묶고, 출처 ID로 중복을 제거한다.
- 타이머와 사람의 승인 응답도 결국 인박스 이벤트로 돌아와 같은 경로로 처리된다.
