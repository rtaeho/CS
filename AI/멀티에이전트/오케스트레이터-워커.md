조정자 역할의 LLM이 작업을 동적으로 쪼개 여러 워커 LLM에 나눠 맡기고, 그 결과를 종합하는 멀티에이전트 구조다.

기준 시점: 2026-11

## 왜 필요한가

단일 에이전트가 복잡한 작업을 혼자 처리하려면 필요한 하위 작업을 미리 다 예측해 하나의 컨텍스트 안에 담아야 한다. [[플래닝]]에서 다루는 plan-and-execute 패턴은 계획을 먼저 세우고 그 순서를 따라가지만, 여러 파일을 복잡하게 고쳐야 하는 코딩 작업처럼 어떤 하위 작업이 필요할지 미리 예측할 수 없는 경우에는 계획 자체가 입력에 따라 계속 달라져야 한다. 오케스트레이터-워커 패턴은 "중앙의 LLM이 작업을 동적으로 나누어 워커 LLM에 맡기고, 그 결과를 종합"하는 방식으로 이 문제를 푼다.

## parallelization과의 차이

구조는 비슷하지만 유연성이 다르다. parallelization은 하위 작업이 미리 정해져 있는 반면, 오케스트레이터-워커는 하위 작업이 미리 정해지지 않고 오케스트레이터가 입력에 따라 그때그때 정한다.

## 동작 과정

```
사용자 질의
   │
   ▼
[리드 에이전트 (오케스트레이터)] ── 계획을 [[에이전트 메모리]]에 저장
   │                                  (컨텍스트가 잘려도 계획은 남는다)
   │  목표·출력 형식·쓸 도구·작업 경계를 정해 서브에이전트 생성
   ├──▶ [서브에이전트 1] ── 도구 반복 호출 → 결과를 압축해 반환
   ├──▶ [서브에이전트 2] ── 도구 반복 호출 → 결과를 압축해 반환
   └──▶ [서브에이전트 N] ── 도구 반복 호출 → 결과를 압축해 반환
   │
   ▼
리드 에이전트가 결과를 종합, 필요하면 서브에이전트를 더 생성
   │
   ▼
(필요하면) 별도 에이전트가 출처를 표시
```

앤트로픽의 멀티 에이전트 리서치 시스템이 구체적인 예다. [[서브에이전트와 컨텍스트 격리|서브에이전트는 "intelligent filters" 역할을 하며, 모은 정보를 압축해 리드 에이전트에 돌려준다]].

## 서브에이전트 수를 정하는 규칙

앤트로픽은 프롬프트에 작업 종류별 규칙을 넣었다고 설명한다: 단순 사실 확인은 에이전트 1개와 도구 호출 3~10회, 직접 비교는 서브에이전트 2~4개(각 10~15회), 복잡한 리서치는 역할을 나눈 서브에이전트 10개 이상. 리드는 서브에이전트 3~5개를 병렬로 띄우고, 각 서브에이전트는 도구 3개 이상을 병렬로 호출하도록 했다.

## 왜 성능이 오르는가

내부 리서치 평가에서 Opus 4 리드 + Sonnet 4 서브에이전트 구성이 단일 Opus 4 에이전트보다 90.2% 우위를 보였다. BrowseComp 평가에서는 토큰 사용량이 성능 차이의 약 80%를, 도구 호출 수와 모델 선택이 나머지를 더해 전체 차이의 95%를 설명했다. 병렬화로 복잡한 질의의 리서치 시간을 최대 90% 줄였다고 밝혔다. 여러 독립적인 방향을 동시에 조사해야 하는, 범위가 넓은 질의에 특히 강하다고 설명한다.

## 트레이드오프

- **토큰 비용**: 에이전트는 채팅보다 약 4배, 멀티 에이전트 시스템은 약 15배 토큰을 쓴다. 작업의 가치가 이 비용을 감당할 만큼 커야 경제적으로 타당하다.
- **적용 범위**: 모든 에이전트가 같은 컨텍스트를 공유해야 하거나 작업 간 의존성이 많은 영역(예: 대부분의 코딩 작업)에는 현재 적합하지 않다고 설명한다.

## 주의사항

초기에는 리드가 "research the semiconductor shortage"처럼 짧은 지시만 내려 서브에이전트가 작업을 잘못 해석하거나 같은 검색을 반복하는 문제가 있었다. 각 서브에이전트에 목표·출력 형식·쓸 도구와 출처·작업 경계를 명확히 주는 상세한 작업 설명으로 중복과 공백을 줄였다고 밝혔다. 그 외에 흔한 실패 모드로는 다음이 꼽힌다.

- 단순한 질의에 서브에이전트 50개를 생성하는 과도한 확장
- 존재하지 않는 출처를 끝없이 찾아 헤매는 탐색
- 서브에이전트끼리 서로에게 과도한 업데이트를 보내 방해하는 문제
- 충분한 결과가 있는데도 계속 진행하거나 지나치게 장황한 검색어를 쓰는 문제
- SEO 중심 콘텐츠를 학술 자료 같은 권위 있는 출처보다 우선하는 문제
- 서브에이전트끼리 같은 작업을 중복 수행하는 문제

## 핵심 정리

- 오케스트레이터-워커는 하위 작업을 미리 예측할 수 없는 복잡한 작업에서, 중앙 LLM이 입력에 따라 동적으로 작업을 나누고 결과를 종합하는 구조다
- parallelization과 구조는 비슷하지만, 하위 작업을 미리 정해두지 않고 오케스트레이터가 그때그때 정한다는 점이 다르다
- 성능은 오르지만(내부 평가 90.2% 우위) 토큰 비용도 크게 늘어나므로(멀티 에이전트 기준 채팅 대비 약 15배), 작업 가치가 그 비용을 감당할 만한 경우에 써야 한다
