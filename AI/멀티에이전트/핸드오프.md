한 에이전트가 대화의 제어권을 다른 에이전트에게 완전히 넘기는 것으로, 넘기는 쪽이 지금까지의 대화 기록과 맥락 중 무엇을 받는 쪽에 들려줄지를 명시적으로 설계해야 한다.

기준 시점: 2026-11

## 왜 필요한가

고객 지원처럼 주문 조회·환불·FAQ 같은 서로 다른 전문 영역을 한 에이전트가 전부 맡으면 프롬프트가 비대해지고 각 영역의 품질이 떨어진다. 영역별로 전문 에이전트를 두고 접수(triage) 에이전트가 적절한 쪽으로 넘기면 각 에이전트는 자기 역할에만 집중할 수 있다. 문제는 "넘긴다"는 동작 자체다. 그냥 다른 모델을 호출하는 게 아니라, 지금까지의 대화에서 받는 쪽이 무엇을 보고 무엇을 못 보게 할지, 그리고 넘기는 시점에 알아야 할 추가 정보(사유·우선순위 등)를 어떻게 함께 넘길지를 정해야 한다.

## 구조

OpenAI Agents SDK 문서는 핸드오프를 모델에게 툴로 보여준다고 설명한다. `Refund Agent`로의 핸드오프는 모델에게 `transfer_to_refund_agent`라는 이름의 툴로 노출된다. 즉 모델은 "다음 에이전트를 선택하는 것"을 "툴을 호출하는 것"과 똑같은 방식으로 다룬다.

```
Triage Agent
  ├─ 툴: transfer_to_billing_agent  ──▶  Billing Agent
  └─ 툴: transfer_to_refund_agent   ──▶  Refund Agent
                                          (기본값: 이전 대화 전체를 그대로 받음)
```

기본 동작은 받는 쪽 에이전트가 "대화를 통째로 이어받는 것처럼" 이전 대화 전체를 본다. 이게 핵심인데, 체크리스트 항목이 말하는 "함께 넘겨야 하는 상태"가 바로 이 기본값을 그대로 둘지 바꿀지의 문제다.

- **대화 기록**: 기본값은 전체 이력 그대로. `input_filter`를 설정하면 받는 쪽이 보는 입력을 가공할 수 있다 — 예를 들어 `remove_all_tools`는 과거 툴 호출 관련 항목을 모두 제거한다.
- **핸드오프 시점의 메타데이터**: 모델이 핸드오프를 호출하면서 `reason`, `priority` 같은 작은 데이터를 함께 줄 수 있다(`input_type`으로 스키마를 정의). 이건 넘기는 이유를 로그로 남기거나 받는 쪽의 초기 동작을 분기하는 데 쓰지만, 대화 내용 자체를 대체하지는 않는다.
- **애플리케이션 상태**: 모델이 생성하지 않는, 이미 코드가 들고 있는 상태(사용자 ID, DB 커넥션 등)는 핸드오프 메타데이터가 아니라 별도의 컨텍스트 객체(`RunContextWrapper.context`)로 전달한다. 두 경로를 섞으면 안 된다 — 모델이 결정하는 값은 핸드오프 입력으로, 로컬에 이미 있는 값은 컨텍스트로 나눈다.

받는 쪽 에이전트에게 핸드오프를 이해시키려면 프롬프트에 핸드오프가 있다는 사실과 사용법을 안내하는 문구를 넣으라고 권한다(SDK는 이런 추천 문구를 템플릿으로 제공한다).

## 트레이드오프

- 대화 기록을 그대로 넘기면 받는 쪽이 맥락을 놓치지 않지만, 이전 에이전트의 툴 호출 로그나 무관한 내부 추론까지 같이 넘어가 받는 쪽의 컨텍스트를 불필요하게 채운다.
- `input_filter`로 걸러내면 컨텍스트는 깨끗해지지만, 받는 쪽이 필요한 세부를 놓쳐 같은 질문을 사용자에게 다시 하게 될 위험이 있다.
- 핸드오프는 제어권을 완전히 넘기고 돌아오지 않는 구조라서, 원래 에이전트가 계속 조율해야 하는 작업에는 맞지 않는다. 그런 경우는 [[오케스트레이터-워커]]처럼 위임한 뒤 결과를 돌려받아 계속 진행하는 구조를 쓴다.

## 주의사항

- 가능한 목적지가 여러 개면 목적지마다 핸드오프를 하나씩 등록해 모델이 그중 하나를 고르게 한다. 하나의 핸드오프 안에서 메타데이터로 목적지를 분기하는 방식은 지원되지 않는다.
- 입력 가드레일은 체인의 첫 에이전트에만, 출력 가드레일은 최종 결과를 내는 에이전트에만 적용된다. 핸드오프로 넘어간 중간 에이전트의 각 툴 호출을 검사하려면 별도의 툴 가드레일이 필요하다.

## 핵심 정리

핸드오프는 "누가 대화를 이어받는가"를 모델이 툴 호출로 직접 고르게 하는 패턴이고, 넘기는 작업의 절반은 받는 쪽에게 얼마나 많은 과거 맥락과 어떤 추가 메타데이터를 들려줄지를 설계하는 일이다. 기본값(전체 이력 그대로)에 안주하지 않고 `input_filter`·`input_type`·컨텍스트 전달을 구분해 쓰는 게 핵심이다.
