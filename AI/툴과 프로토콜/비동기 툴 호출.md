비동기 툴 호출은 오래 걸리는 툴이 결과 대신 작업 핸들을 즉시 돌려주고, 클라이언트가 그 핸들로 상태를 물어 결과를 나중에 받는 방식으로, 에이전트 루프가 한 번의 툴 호출에 묶여 멈추지 않게 한다.

기준 시점: 2026-11

## 왜 필요한가

[[함수 호출]]의 기본 모양은 동기다. 모델이 툴을 부르면 하네스는 결과가 올 때까지 기다리고, 결과 하나를 받아 다음 턴으로 넘긴다. 몇 초짜리 검색이면 문제가 없지만 빌드·대규모 조사·데이터 처리처럼 몇 분에서 몇 시간 걸리는 툴이면 세 가지가 깨진다.

```
동기 툴 호출
  모델 ──tools/call──▶ 서버  (빌드 20분)
  │                    │
  │  ……20분 동안 에이전트 루프가 멈춤……
  │                    │
  ◀────── 결과 ────────┘
  문제 1) 그동안 에이전트는 다른 일을 못 한다
  문제 2) HTTP 요청 하나가 20분 열려 있어야 한다 → 프록시·타임아웃에 끊긴다
  문제 3) 끊기면 결과도, 작업이 끝났는지 여부도 모른다
```

[[에이전트 루프]]가 툴 하나를 기다리며 멈추는 셈이다. 그래서 예전에는 서버가 "작업 시작" 툴과 "상태 확인" 툴을 따로 만들고, 모델이 스스로 상태 확인 툴을 반복해서 부르게 했다. 이러면 폴링 한 번이 모델의 한 턴이 되어 토큰과 시간이 들고, 언제 다시 물어볼지를 모델이 짐작해야 한다. 비동기 툴 호출은 이 폴링을 프로토콜과 클라이언트(하네스) 쪽으로 내려, 모델은 "결과가 준비됐다"는 사실만 받게 한다.

## 구조

핵심은 "결과" 자리에 "작업 핸들"이 올 수 있게 응답 타입을 넓히는 것이다. [[MCP]]의 Tasks 확장이 이 구조를 표준으로 정했고, Claude Code 문서가 클라이언트 쪽 동작을 자세히 적어 두었다.

```
클라이언트(하네스)                         MCP 서버
  │  tools/call  + 확장 선언                  │
  │  (_meta 안에 io.modelcontextprotocol/tasks) │
  │─────────────────────────────────────────▶│ 작업 접수
  │◀─────────────────────────────────────────│ resultType: "task"
  │   taskId, status: working, pollIntervalMs │ (일은 아직 안 함)
  │                                          │
  │  (모델은 다른 일을 계속한다)                  │ …작업 진행…
  │                                          │
  │  tasks/get {taskId}  ── 폴링 간격마다 ────▶│
  │◀── status: working, statusMessage ───────│
  │                                          │
  │  tasks/get {taskId} ────────────────────▶│
  │◀── status: input_required, inputRequests ─│ 사람 확인이 필요
  │  tasks/update {inputResponses} ─────────▶│ (elicitation/create)
  │                                          │
  │  tasks/get {taskId} ────────────────────▶│
  │◀── status: completed, result ────────────│
  │                                          │
  └─ 결과를 모델에 툴 결과로 넘긴다
```

### 협상

서버가 아무 때나 작업 핸들을 돌려주면 그걸 모르는 클라이언트는 깨진다. 그래서 클라이언트가 요청마다 "나는 작업 핸들을 받을 수 있다"고 선언하고, 서버는 그 선언이 있는 `tools/call`에만 작업으로 답한다. Claude Code 문서에 따르면 2026-07-28 프로토콜 개정판으로 협상된 연결에서 클라이언트 기능이 `params._meta["io.modelcontextprotocol/clientCapabilities"]`의 `extensions`에 `"io.modelcontextprotocol/tasks": {}`로 실리고, 선언이 없는데 작업으로 답하면 `Unsupported result type 'task' for tools/call` 오류가 난다.

### 작업 핸들

| 필드 | 뜻 |
| --- | --- |
| `resultType` | `"task"`면 작업 핸들, 없으면 일반 결과로 읽는다 |
| `taskId` | 작업 식별자. 이후 모든 상태 조회의 열쇠 |
| `status` | 현재 상태 |
| `createdAt`, `lastUpdatedAt` | 생성·마지막 갱신 시각 |
| `ttlMs` | 서버가 작업과 결과를 보관하는 시간. `null`이면 제한 없음 |
| `pollIntervalMs` | 서버가 권하는 폴링 간격(선택) |
| `statusMessage` | "212개 중 40개 컴파일" 같은 진행 설명(선택) |

### 상태

```
            ┌──────────────┐
            │   working    │◀───────────┐
            └──────┬───────┘            │ tasks/update로 답함
       ┌───────────┼───────────┬────────┴─────────┐
       ▼           ▼           ▼                  │
  completed     failed     cancelled      input_required
  (result)      (error)                    (inputRequests)
```

- `working` — 계속 폴링한다.
- `input_required` — 서버가 `inputRequests`에 넣은 요청(예: `elicitation/create`로 사람에게 승인 받기)에 `tasks/update`로 답한다. 오래 도는 작업이 중간에 사람에게 묻고 이어가는 흐름이 여기서 나온다.
- `completed` / `failed` / `cancelled` — 끝 상태. 결과나 오류를 모델에 넘긴다.

사용자나 모델이 작업을 멈추면 클라이언트는 `tasks/cancel`을 보낸다.

## 구현

서버 쪽 핵심은 **요청을 받자마자 작업을 등록하고 핸들부터 돌려준 뒤 일을 시작하는 것**이다. 결과를 계산하고 나서 답하면 비동기로 만든 의미가 없다. 아래는 프로토콜 세부(서명·세션 등)를 덜어낸 개념 스케치다.

```python
import asyncio, uuid
from datetime import datetime, timezone

TASKS: dict[str, dict] = {}   # 실제로는 재시작에도 남는 저장소에 둔다

def now() -> str:
    return datetime.now(timezone.utc).isoformat()

async def run_build(task_id: str, args: dict) -> None:
    task = TASKS[task_id]
    try:
        for done in range(0, 101, 10):
            task.update(statusMessage=f"{done}% 완료", lastUpdatedAt=now())
            await asyncio.sleep(1)
        task.update(status="completed", lastUpdatedAt=now(),
                    result={"content": [{"type": "text", "text": "빌드 성공"}]})
    except Exception as e:
        task.update(status="failed", lastUpdatedAt=now(),
                    error={"code": -1, "message": str(e)})

async def handle_tools_call(params: dict) -> dict:
    caps = params.get("_meta", {}).get("io.modelcontextprotocol/clientCapabilities", {})
    supports_tasks = "io.modelcontextprotocol/tasks" in caps.get("extensions", {})
    if not supports_tasks:
        return await run_sync(params)          # 선언이 없으면 예전처럼 동기로 (생략)

    task_id = f"build-{uuid.uuid4().hex[:8]}"
    TASKS[task_id] = {"taskId": task_id, "status": "working",
                      "createdAt": now(), "lastUpdatedAt": now(),
                      "ttlMs": 60 * 60 * 1000 * 2}   # 작업 시간 + 결과 보관 시간
    asyncio.create_task(run_build(task_id, params["arguments"]))   # 일은 뒤에서
    return {"resultType": "task", **TASKS[task_id], "pollIntervalMs": 10_000}

async def handle_tasks_get(params: dict) -> dict:
    return {"resultType": "complete", **TASKS[params["taskId"]]}
```

## 트레이드오프

| 얻는 것 | 내주는 것 |
| --- | --- |
| 에이전트 루프가 긴 툴에 묶이지 않는다 | 서버가 작업 상태를 저장·보관해야 한다(상태 있는 서버) |
| 연결이 끊겨도 `taskId`로 다시 물을 수 있다 | 폴링 간격만큼 결과 전달이 늦어진다 |
| 진행 상황(`statusMessage`)을 보여줄 수 있다 | 취소·만료·재시도 같은 상태 처리 코드가 늘어난다 |
| 중간에 사람 입력을 받는 긴 작업을 표준 방식으로 만든다 | 클라이언트가 확장을 지원해야 한다(협상 실패 시 동기로 내려야 함) |

폴링 대신 서버가 끝났을 때 알려주는 푸시(웹훅, [[SSE]])도 가능하지만, 폴링은 클라이언트가 방화벽 뒤에 있거나 잠시 꺼져 있어도 다시 켜졌을 때 물어보면 된다는 점에서 단순하다. 지연을 줄이려면 서버가 `pollIntervalMs`로 간격을 조절하게 하는 편이 실용적이다. 사용자가 느끼는 지연 전반은 [[지연 시간 설계]]에서 다룬다.

## 주의사항

- **핸들을 먼저, 일은 나중에.** Claude Code 문서는 HTTP 서버라면 요청별 타이머 안에 작업 응답을 먼저 보내고 그 뒤에 일을 하라고 안내한다. 핸들 응답이 늦으면 결국 동기 호출과 같은 타임아웃에 걸린다.
- **결과를 충분히 오래 보관한다.** 클라이언트가 잠시 꺼졌다 돌아올 수 있다. Claude Code 문서는 끝난 작업의 결과를 최소 한 시간 보관하라고 권하고, `ttlMs`에는 생성 시점부터의 보관 시간(예: 30분 작업 + 1시간 보관이면 5,400,000)을 적으라고 한다.
- **"결과를 모름"과 "실패"를 구분한다.** 서버가 `taskId`를 모르게 되면(재시작으로 상태를 잃는 등) 작업이 끝났는지 알 수 없다. Claude Code는 이 경우를 `outcome unknown`으로 보고하고, 다시 호출하면 일을 두 번 할 수 있으니 먼저 서버에 확인하라고 경고한다. 재시도해도 안전하도록 툴을 [[멱등성]] 있게 만들거나 작업 저장소를 재시작에도 남게 두는 것이 좋다.
- **폴링 간격을 너무 짧게 잡지 않는다.** Claude Code 문서는 1분 넘는 작업에는 10,000~30,000ms, 짧은 작업에는 2,000ms를 권한다. 클라우드 밖에서는 서버 값을 250~30,000ms로 제한하고 값이 없으면 2,000ms를 쓴다고 한다.
- **`input_required`는 사람이 없을 수도 있다.** 비대화형 실행(`claude -p` 같은 한 번짜리 실행)에서는 사람에게 물을 수 없으므로, 문서에 따르면 Claude Code는 이런 요청을 받으면 작업 취소를 요청한다. 승인이 꼭 필요한 작업이라면 승인 없이 진행하지 않도록 서버가 설계돼 있어야 한다.
- **클라이언트가 지원하지 않는 경우를 남겨 둔다.** 확장 선언이 없는 요청에는 동기로 답하거나, 작업 시작·상태 확인 툴을 따로 두는 예전 방식으로 내려가는 경로가 있어야 한다.

## 핵심 정리

- 오래 걸리는 툴은 결과 대신 작업 핸들(`taskId`, `status`)을 즉시 돌려주고, 클라이언트가 `tasks/get`으로 폴링해 결과를 받는다.
- 폴링을 모델이 아니라 하네스가 맡으므로 모델의 턴과 토큰을 아끼고, 에이전트 루프는 그동안 다른 일을 한다.
- 상태는 `working`·`input_required`·`completed`·`failed`·`cancelled`이고, `input_required`로 긴 작업 도중 사람 입력을 받는다.
- 서버는 핸들부터 답하고, 결과를 충분히 보관하고, 재시도해도 안전하게 만들어야 한다.
- 클라이언트가 확장을 선언했을 때만 작업으로 답하고, 아니면 동기 방식으로 내려간다.
