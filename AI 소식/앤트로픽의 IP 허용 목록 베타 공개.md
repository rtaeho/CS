앤트로픽이 Claude Console에서 조직 단위 IP 허용 목록(IP allowlist)을 설정해, 목록 밖 주소에서 온 API 요청과 접속을 거부하는 기능을 베타로 공개했다.

기준 시점: 2026-11-05

## 무슨 일인가

Claude Platform 릴리스 노트에 따르면 2026년 11월 5일 조직용 IP 허용 목록이 베타로 나왔다. 릴리스 노트는 목록에 없는 주소에서 온 요청은 거부되므로 "유출된 API 키를 쓸 수 있는 곳이 제한된다"고 설명한다. IPv4·IPv6 주소나 CIDR 범위를 조직당 최대 1,000개까지 넣을 수 있다.

설정 문서가 밝힌 동작은 이렇다.

- **비교 대상은 요청의 공인 IP다.** 조직 관리자(admin)나 소유자(owner)가 조직 전체에 적용되는 범위 목록을 만들고, 앤트로픽은 적용 대상 요청마다 공인 IP를 목록과 비교해 맞지 않으면 거부한다. Messages API는 403 `permission_error`와 `Your IP address isn't in this organization's allowed range.` 메시지를 돌려준다.
- **적용 범위.** Claude Console 화면, Messages·Message Batches·Token Counting·Models·Files·Skills API, Managed Agents의 Agents·Sessions·Environments·Vaults·Memory stores 엔드포인트, Admin API와 Compliance API가 대상이다. API 키와 Workload Identity Federation 토큰 둘 다 막힌다.
- **적용되지 않는 곳.** Managed Agents 엔드포인트 호출만 막을 뿐 에이전트 런타임 안의 네트워킹에는 적용되지 않는다. Amazon Bedrock, Claude Platform on AWS, Google Cloud, Microsoft Foundry를 거치는 호출에도 적용되지 않는다.
- **입력 규칙.** 단일 주소(`203.0.113.5`)나 CIDR 범위(`203.0.113.0/24`, `2001:db8::/32`)를 넣되, IPv4는 `/8`, IPv6는 `/32`보다 넓게 잡을 수 없다. `10.0.0.0/8` 같은 사설 대역이 아니라 트래픽이 네트워크를 빠져나가는 공인 주소를 넣어야 한다.
- **잠김 방지.** 저장할 때 지금 접속한 주소가 목록에 있는지만 확인하고, 서버·팀원·내일 접속할 주소는 확인하지 않는다고 문서는 경고한다. 그래서 "관리자는 어떤 IP에서든 이 설정 페이지에 접근 허용" 체크박스를 켜 두길 권하는데, 관리자 세션을 탈취한 공격자도 원격에서 목록을 바꿀 수 있다는 단점을 함께 적었다. 변경은 적용까지 최대 15분이 걸린다.

문서는 허용 목록이 "키가 어디서 동작하는지는 제한하지만 얼마나 오래 동작하는지는 제한하지 않는다"며, 짧은 키 만료를 함께 쓰거나 Workload Identity Federation으로 옮겨 정적 키를 쓰지 않는 편이 허용 목록만 쓰는 것보다 안전하다고 밝혔다.

## 왜 중요한가

API 키는 정적 비밀번호라 한 번 새면 어디서든 쓸 수 있다. 저장소에 실수로 커밋된 키, 로그에 찍힌 키가 공격자 손에 들어가면 요금과 데이터가 함께 샌다. IP 허용 목록은 "키를 아는 것"에 "정해진 네트워크에서 왔다는 것"을 조건으로 하나 더 얹어, 키가 새도 쓸 수 있는 곳을 줄인다.

에이전트를 운영하는 쪽에서는 몇 가지가 달라진다.

- 모델 호출이 나가는 공인 주소를 알아야 한다. 컨테이너·서버리스 환경은 [[NAT]] 게이트웨이를 거쳐 나가므로 그 게이트웨이의 고정 주소를 넣어야 하고, 자동 확장으로 나가는 주소가 바뀌는 구조라면 먼저 출구 주소를 고정해야 한다.
- 문서는 하루나 일주일에 한 번만 도는 작업까지 403을 지켜보라고 권한다. 배치 평가나 야간 에이전트 작업은 설정 직후에는 문제가 드러나지 않다가 며칠 뒤에 깨질 수 있다.
- 공유 [[프록시]] 주소를 넣으면, 그 프록시를 쓸 수 있는 공격자는 유출된 키로 여전히 요청할 수 있다고 문서는 경고한다. 허용 목록은 출구가 좁을수록 효과가 있다.
- 클라우드 플랫폼(Bedrock 등)을 거치는 호출과 Managed Agents 런타임 내부 네트워킹은 적용 대상이 아니므로, 그쪽 보안은 각 플랫폼의 네트워크 정책으로 따로 잡아야 한다.

## 짚고 갈 개념

- [[CIDR]] — `203.0.113.0/24`처럼 주소 범위를 슬래시와 네트워크 비트 수로 적는 표기. 이번 기능은 IPv4 `/8`, IPv6 `/32`보다 넓은 범위를 받지 않는다
- [[NAT]] — 사설 대역 서버들이 하나의 공인 주소로 나가게 하는 변환. 허용 목록에는 사설 주소가 아니라 NAT를 거쳐 나가는 공인 주소를 넣어야 한다
- [[프록시]] — 요청을 대신 중계하는 서버. 프록시를 거치면 앤트로픽에는 프록시의 주소가 보이므로, 공유 프록시를 목록에 넣으면 그 프록시 사용자 전체가 통과한다

## 내 생각

문서가 허용 목록을 "단독으로는 부족한 방어"로 스스로 규정한 점이 눈에 띈다. 위치 제한은 키 유출의 피해 범위를 줄일 뿐 키가 오래 사는 문제는 그대로 두므로, 결국 방향은 짧은 수명의 토큰을 발급받는 Workload Identity Federation 쪽으로 보인다. 관리자 예외 체크박스는 잠김 위험과 탈취 위험을 맞바꾸는 선택인데, 문서가 Compliance API의 Activity Feed로 목록 변경을 감사하라고 짝지어 둔 것을 보면 "막기"보다 "바뀌면 알아채기"로 그 틈을 메우려는 설계로 보인다.
