앤트로픽이 Claude Enterprise 조직의 모든 프롬프트와 툴 호출을 모델이 돌기 전에 조직의 보안 서버로 보내 허용·거부 판정을 받게 하는 Inference hooks를 베타에서 정식으로 전환했다.

기준 시점: 2026-10-20

## 무슨 일인가

Claude 플랫폼 릴리스 노트는 2026년 10월 20일 항목에서 Inference hooks가 Claude Enterprise 조직 대상으로 베타를 벗어났다고 밝혔다. 공식 문서가 설명하는 구조는 이렇다.

- **어디서 도는가.** 훅은 사용자 기기가 아니라 앤트로픽 서버에서, 요청이 클라이언트를 떠난 뒤 모델이 돌기 전에 실행된다. 그래서 claude.ai, Cowork, Claude Code, Claude for Microsoft 365, Claude Tag, Claude in Chrome 등 조직의 Claude 제품 전체에 훅 하나가 똑같이 적용되고, 기기에 설치할 것이 없다고 문서는 설명한다. Amazon Bedrock·Google Cloud와 API로 쓰는 Claude Platform 조직은 대상이 아니다.
- **언제 걸리는가.** 이벤트는 두 가지다. `prompt`는 추론 요청마다 한 번, 추론 시작 전에 걸린다. `tool_call`은 **Validate tool calls**를 켠 조직에서 Claude의 응답에 툴 호출이 들어 있을 때, 어떤 툴도 실행되기 전에 걸리고 한 응답의 툴 호출 전체를 판정 하나로 덮는다. 툴 결과가 돌아오는 시점도 다음 `prompt` 판정 대상이 된다.
- **무엇을 주고받는가.** 앤트로픽은 대화 기록을 HTTPS `POST`로 조직이 운영하는 "AI 보안 서버"에 보내고, 요청은 Standard Webhooks 규격으로 서명된다. 서버는 `{"action": "allow"}` 같은 작은 JSON 판정을 돌려준다. 거부하면 요청은 모델에 닿지 않고, 사용자는 서버가 준 `deny_reason`과 관리자가 정한 안내 문구(최대 500자)를 합친 차단 메시지를 본다. 서버는 사용자가 보는 것(대화 텍스트, 툴 호출과 결과, 첨부에서 뽑은 텍스트)만 받고 원본 파일·이미지 바이트, 시스템 프롬프트, 툴 정의는 받지 않는다.
- **서버가 늦거나 죽으면.** 판정 제한 시간은 1~10,000ms, 기본 5,000ms다. 시간 안에 판정이 없으면 조직이 고른 실패 처리를 따른다. **Block the request**(fail closed)는 추론을 멈추고, **Allow the request**(fail open)는 검사 없이 통과시킨다. 처음 엔드포인트를 저장할 때 기본값은 Allow the request다. 서버 탓 실패가 이어지면 서킷 브레이커가 끊겨 서버 호출을 멈추고 모든 요청에 실패 처리를 적용한다. 끊긴 지 3분 뒤부터 대략 1분에 한 번씩 백그라운드 시험 요청을 보내 유효한 판정이 오면 자동으로 다시 붙는다.
- **켜는 순서.** 강제 적용을 끈 상태, 판정만 받고 아무것도 막지 않는 **Shadow mode**, 실제로 막는 상태 세 단계가 있다. 검사할 요청 비율(0~100%)과 역할별 제외도 정할 수 있어, 첫날부터 모두를 막지 않고 단계적으로 적용하게 했다.

문서는 가장 흔한 용도로 DLP(규제·기밀 자료가 담긴 프롬프트 차단)를 들고, 실시간 대화 보관, 프롬프트 사용량 측정, 자체 정책 엔진(모델 허용 목록, 근무 시간 제한 등)을 함께 꼽았다. 판정은 허용·거부 둘뿐이라 프롬프트를 고쳐 쓰거나 일부를 가리는 것은 지원하지 않는다. 사후 감사용 Compliance API와는 "추론 전에 막는다"와 "일어난 뒤 조회한다"로 역할을 나눴다.

## 왜 중요한가

에이전트에 가드레일을 붙일 때 늘 걸리는 질문이 "검사를 어디에 둘 것인가"다. 이 기능은 그 답을 클라이언트도, 각 툴 서버도 아닌 **모델 호출 직전의 중계 지점**에 두었다.

- **우회 경로가 줄어든다.** 검사를 각 앱이나 사용자 기기에 넣으면 제품마다 따로 만들어야 하고 빠진 곳이 생긴다. 추론 요청이 반드시 지나는 지점에 두면 웹·데스크톱·CLI·Slack 어디서 온 요청이든 같은 정책을 지난다.
- **툴 호출도 실행 전에 본다.** 프롬프트만 보면 "무엇을 물었나"만 알 수 있다. 에이전트의 사고는 대개 "무엇을 실행했나"에서 나므로, 툴 호출을 실행 전에 판정받는 `tool_call` 이벤트가 에이전트 환경에서는 더 중요하다.
- **안전 장치 자체의 장애를 설계에 넣었다.** 검사 서버가 죽으면 막을 것인가 통과시킬 것인가(fail closed / fail open), 계속 실패하면 언제 끊고 언제 다시 붙을 것인가([[서킷 브레이커]]), 새 정책을 어떻게 실제 트래픽에 시험할 것인가(섀도 모드, 비율 적용). 직접 가드레일을 만들 때도 똑같이 정해야 하는 항목들이 설정 화면에 그대로 드러나 있다.

## 짚고 갈 개념

- 가드레일 — 입출력을 검증해 에이전트 사고의 범위를 좁히는 층. Inference hooks는 그 검증을 모델 호출 직전에 두는 사례다
- 서킷 브레이커 — 연속 실패한 대상의 호출을 잠시 끊어 장애가 번지지 않게 하는 패턴 ([[서킷 브레이커]])
- Fail-open과 Fail-closed — 안전 장치가 응답하지 않을 때 요청을 통과시킬지 막을지 정하는 설계와, 섀도 모드·비율 적용으로 전환 위험을 줄이는 방법

## 내 생각

기본값이 fail open(Allow the request)인 점이 눈에 띈다. 보안 서버 하나가 느려졌다고 조직 전체의 Claude 사용이 멈추는 것을 더 큰 위험으로 본 선택으로 보인다. 다만 DLP처럼 "새면 안 되는" 용도라면 기본값 그대로 두는 순간 서버 장애가 곧 검사 공백이 되므로, 도입하는 쪽이 실패 처리를 의식적으로 골라야 할 것으로 보인다. 문서가 fail open으로 통과된 요청을 감사 기록에 따로 남기게 한 것도 그 공백을 나중에라도 추적하라는 뜻으로 읽힌다.

판정이 허용·거부 둘뿐이고, 거부된 내용이 이후 요청마다 대화 기록에 다시 실려 계속 거부될 수 있다는 점(문서가 제품별로 거부된 메시지를 지우고 이어가는 방법을 따로 안내한다)도 실제 운영에서 사용자 경험을 꽤 좌우할 것으로 보인다. 가리기(redaction)를 지원하지 않는 한 훅은 "통과 아니면 멈춤"이라, 정책을 섀도 모드로 충분히 다듬고 들어가는 것이 사실상 필수로 보인다.
