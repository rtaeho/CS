앤트로픽이 Messages API에 대화 상태를 서버에 잠시 보관해 매 턴 전체 대화를 다시 보내지 않게 하는 Message Threads 베타를 공개했다.
기준 시점: 2026-11-02

## 무슨 일인가

앤트로픽 공식 문서에 따르면 2026년 11월 2일 Messages API에 Message Threads 베타가 올라왔다. 스레드가 없으면 매 턴마다 전체 대화를 다시 올리고 API가 그 전부를 다시 검증·토큰화해야 하는데, 스레드를 쓰면 이 작업의 대부분이 새 턴만 처리하는 것으로 줄어든다고 설명한다.

동작 방식은 생성(create)과 이어가기(continue) 두 단계다. 첫 요청에는 전체 대화·`system`·`tools`를 평소처럼 보내고 `"thread": {"type": "create"}`를 추가하면, API가 Claude의 응답을 포함해 그 대화를 응답 `id` 밑에 저장한다. 다음 턴부터는 이전 응답 이후의 새 메시지만 보내고 `"thread": {"type": "continue", "previous_message_id": "<이전 id>"}`를 넣으면 되며, 이때 `system`과 `tools`는 생략한다(보내면 400 에러). 이 기능을 쓰려면 모든 요청에 `message-threads-2026-08-12` 베타 헤더를 넣어야 한다.

스레드는 "best-effort"다. 마지막 요청 후 5분이 지나면 만료되고, 마지막 사용 후 늦어도 1시간 안에 삭제된다. continue 요청이 이어갈 수 없으면 404(`thread_not_found`)를 돌려주는데, 이때는 클라이언트가 보관해 둔 전체 대화를 새 create 요청으로 다시 보내 이어가야 한다. 문서는 "애플리케이션이 대화의 source of truth로 남아야 한다"고 못박고, API의 어떤 응답도 그 턴이 실제로 저장됐는지 알려주지 않는다고 설명한다.

스레드는 이어붙이기(append-only)만 가능해서 각 응답 `id`는 한 번만 이어갈 수 있고, 중간 턴을 수정하거나 분기하려면 새 스레드를 시작해야 한다. `model`, `tool_choice`, `thinking`, `cache_control` 같은 "고정(fixed)" 필드는 스레드의 모든 요청에서 같은 값을 유지해야 하며 값이 다르면 400 에러(`thread_fingerprint_mismatch`)가 난다. 프롬프트 캐싱은 스레드가 대신 해 주지 않고 평소처럼 직접 `cache_control` 브레이크포인트를 둬야 하며, 스레드가 있는 요청은 브레이크포인트를 최대 4개까지만 허용한다.

가격과 요청 제한(rate limit)은 바뀌지 않는다고 명시한다. 데이터 보존 측은 스레드 내용(대화·시스템 프롬프트·툴)을 서버 관리 키로 암호화해 메모리에만 두고 내구성 있는 저장소에는 쓰지 않으며, 마지막 사용 후 늦어도 1시간 안에 지운다고 설명하지만, 이 기능 자체는 제로 데이터 리텐션(ZDR) 대상이 아니다. HIPAA 준비(readiness)를 켠 조직이나 Inference hooks를 쓰는 조직도 이 기능을 쓸 수 없다. Message Batches, 토큰 카운팅, Compaction 기능과도 함께 쓸 수 없다.

## 왜 중요한가

긴 에이전트 루프는 매 턴 전체 대화를 다시 올리는 방식이 누적될수록 요청이 커지고 첫 토큰까지의 지연이 늘어나는 구조적 비용을 안고 있다. Message Threads는 이 업로드·검증 비용을 줄이는 쪽으로 접근하지만, 토큰 처리량과 가격은 그대로 두고 지연만 줄인다는 점, 그리고 애플리케이션이 여전히 전체 대화를 직접 보관해야 한다는 점에서 "서버가 대화를 대신 기억해 주는 기능"이 아니라 "업로드를 아껴 주는 캐시"에 가깝다. ZDR·HIPAA 조직은 쓸 수 없다는 제약도 지연 최적화와 데이터 보존 요건이 서로 트레이드오프 관계에 있음을 보여준다.

## 짚고 갈 개념

- 프롬프트 캐싱 — 반복되는 프롬프트 앞부분을 캐시에 저장해 비용과 지연을 줄이는 방법. Message Threads는 이걸 대신해 주지 않고, 쓰려면 직접 `cache_control` 브레이크포인트를 둬야 한다
- 제로 데이터 리텐션(ZDR) — API 요청·응답을 서버에 저장하지 않는 데이터 보존 정책. Message Threads는 대화를 짧게라도 서버에 쥐고 있어 ZDR 대상이 아니다

## 내 생각

스레드가 "best-effort"이고 저장 여부를 응답이 알려주지 않는다는 설계가 흥미롭다. 결국 클라이언트가 전체 대화의 사본을 들고 있다가 아무 때나 복구(replay)할 수 있어야 한다는 전제가 깔려 있는데, 이는 상태를 서버로 옮기는 기능이라기보다 "같은 상태를 두 곳에 들고 있으면서 평소엔 가벼운 쪽만 쓰는" 캐싱 계층으로 보는 쪽이 더 맞는 것 같다. 가격이 그대로라는 점도 이 기능의 목적이 비용 절감이 아니라 순수하게 지연 시간 설계에 있다는 것을 보여준다.
