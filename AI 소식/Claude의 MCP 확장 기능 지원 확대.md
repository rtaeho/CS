앤트로픽이 Claude와 Claude Code에서 MCP 서버가 툴과 함께 스킬을 배포하고(Skills over MCP), 오래 걸리는 작업을 백그라운드로 돌리고(Tasks), 호출 도중 사용자에게 입력을 받을 수 있게(Elicitation) 지원을 넓혔다고 밝혔다.

기준 시점: 2026-11-24

## 무슨 일인가

앤트로픽은 2026년 11월 24일 글에서 이번 업데이트로 Claude가 MCP 서버와 "또 하나의 에이전트와 일하듯" 일할 수 있게 됐다고 설명했다. 발표한 기능은 네 가지다.

- **Skills over MCP (공개 베타).** 서버가 툴 옆에 스킬을 함께 게시해 여러 단계 작업을 안내한다. 글은 툴 이름과 설명만으로는 "특정 사용 사례를 어떻게 다룰지"가 드러나지 않는다는 점을 이유로 들었다. Claude는 필요할 때만 스킬을 불러와 컨텍스트 사용을 줄이고, 스킬은 서버와 함께 갱신되므로 사용자가 따로 설치할 것이 없다. 예시로 Shopify(상점 설계·수정), HubSpot(고객 온보딩), Atlassian(조직 맥락 기반 분석)을 들었다. Claude와 Claude Code에서 Pro·Max·Ultra 플랜은 기본으로 켜져 있고, Team 플랜은 관리자가 켜야 하며, Enterprise는 곧 지원한다고 했다.
- **Tasks (정식 출시).** 서버가 시간이 오래 걸리는 작업이나 에이전트 루프 전체를 백그라운드에서 돌리고, Claude는 그동안 다른 일을 하다가 결과가 준비되면 가져온다. 글은 "예전에는 툴 호출이 끝나야 Claude가 다음으로 넘어갈 수 있었다"고 설명했다.
- **Elicitation (정식 출시).** 서버가 호출 도중 멈추고 폼이나 링크로 사용자 입력을 받은 뒤 이어서 진행한다. 돈을 쓰거나 데이터를 지우는 등 승인이 필요한 행동이 용도다. Supabase는 유료 프로젝트 생성과 파괴적인 SQL 실행 전에 비용을 확인하고, GitHub는 에이전트가 저장소를 지우기 전에 사용자가 저장소 이름을 직접 입력하게 한다고 소개했다.
- **File Uploads (곧 출시).** Claude가 PDF·스프레드시트·이미지 같은 파일을 텍스트가 아닌 파일로 MCP 서버에 보내고, 파일은 컨텍스트 창을 거치지 않는다. 실험적 확장이라고 밝혔다.

같은 글은 기반 개선으로 툴 정의를 필요할 때만 불러오는 tool search(여러 서버를 붙인 환경에서 툴 정의의 컨텍스트 사용을 85% 넘게 줄일 수 있다고 밝혔다), Claude 제품 전반의 스테이트리스 스펙 지원, 관리자가 한 번 승인하면 사용자가 자동으로 연결되는 Enterprise Managed Auth를 함께 언급했다. MCP SDK 월간 다운로드가 7억 회를 넘고 Claude용 MCP 커넥터가 1만 개를 넘는다는 수치도 실었다. 이 기능들은 공개 MCP 스펙과 확장의 일부라 Claude 외의 호환 클라이언트도 지원할 수 있다고 덧붙였다.

Claude Code 문서는 Tasks가 프로토콜 수준에서 어떻게 도는지 적어 두었다.

- 2026-07-28 개정판 연결에서 Claude Code는 요청의 `_meta` 안 클라이언트 기능에 `io.modelcontextprotocol/tasks` 확장을 담는다. 서버는 이 확장이 있는 `tools/call`에만 `resultType: "task"`와 `taskId`, `status`를 담은 작업 객체로 답할 수 있고, 없으면 `Unsupported result type 'task' for tools/call` 오류가 난다.
- 작업 응답 직후 Claude Code는 `tasks/get`을 보내고 폴링 간격마다 반복한다. 상태는 `working`, `input_required`, `completed`, `failed`, `cancelled` 다섯 가지다.
- `input_required`면 서버가 넣은 `inputRequests`를 읽어 `tasks/update`로 답한다. 그 안의 `elicitation/create`는 대화형 터미널 세션에서 사람에게 전달된다.
- 클라우드 밖에서는 서버가 준 `pollIntervalMs`를 250~30,000ms로 제한하고 값이 없으면 2,000ms를 쓴다. 문서는 끝난 작업의 결과를 최소 한 시간 보관하라고 권하고, HTTP 서버는 요청 타이머 안에 작업 응답을 먼저 보낸 뒤 일을 하라고 안내한다.

## 왜 중요한가

지금까지 MCP 툴 호출은 함수 호출과 같았다. 부르면 끝날 때까지 기다리고, 결과 하나를 받는다. 이번 세 기능은 이 모양을 각각 다른 방향으로 넓힌다.

- **툴 호출이 "결과"가 아니라 "작업 핸들"을 돌려줄 수 있게 된다.** 몇 분짜리 빌드나 조사를 툴로 만들 때, 지금까지는 서버 쪽에서 작업 ID를 주는 툴과 상태를 묻는 툴을 따로 만들고 모델이 알아서 폴링하게 해야 했다. Tasks는 그 폴링을 클라이언트가 맡게 해, 모델의 컨텍스트와 턴을 아낀다.
- **승인 루프가 서버 안으로 들어온다.** 되돌릴 수 없는 행동 앞에서 사람을 세우는 일을 지금까지는 클라이언트(에이전트 하네스)가 툴 이름을 보고 판단했다. Elicitation은 그 행동이 위험한지 가장 잘 아는 서버가 직접 확인을 요구하게 한다. GitHub 예시처럼 "예/아니오"가 아니라 저장소 이름을 다시 입력하게 하는 식으로 확인 강도도 서버가 정한다.
- **툴 설명에 담기 어려운 절차 지식이 서버와 함께 배포된다.** [[Agent Skills]]를 클라이언트에 따로 깔지 않아도 서버가 자기 툴을 쓰는 순서와 요령을 함께 내려준다. 서버가 갱신되면 사용법도 같이 바뀌므로 툴과 설명서가 어긋날 일이 줄어든다.

## 짚고 갈 개념

- MCP — 모델에 외부 컨텍스트·툴을 붙이는 프로토콜. Elicitation·Tasks·Skills over MCP의 위치가 함께 정리돼 있다 ([[MCP]])
- Agent Skills — SKILL.md 폴더 단위로 에이전트에 절차적 지식을 주고 필요할 때만 불러오는 방식 ([[Agent Skills]])
- 비동기 툴 호출 — 오래 걸리는 툴 호출이 즉시 작업 핸들을 돌려주고 클라이언트가 상태를 폴링해 결과를 받는 패턴, 에이전트 루프가 툴 호출에 묶이지 않게 하는 방법

## 내 생각

Tasks의 `input_required` 상태 안에 `elicitation/create`가 들어가는 구조를 보면, 세 기능이 따로가 아니라 "오래 도는 작업이 중간에 사람에게 물어보고 이어가는" 하나의 흐름을 위해 맞물려 설계된 것으로 보인다. 앤트로픽이 항시 작동 에이전트 가이드에서 설명한 지연된 툴 호출(멈춘 뒤 사용자 응답이 오면 재개)과 비슷한 모양을 이번에는 프로토콜 쪽에서 표준화한 셈으로 읽힌다.

다만 Elicitation으로 서버가 직접 승인을 요구할 수 있게 되면, 사용자 앞에 뜨는 확인 창의 문구를 서버가 쓰게 된다. 악의적이거나 침해된 서버가 그럴듯한 승인 요청으로 사용자를 속이는 경로도 새로 생길 수 있어, 클라이언트가 "이 요청을 어느 서버가 보냈는지"를 얼마나 분명히 보여주느냐가 중요해질 것으로 보인다.
