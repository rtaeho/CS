앤트로픽이 `2023-06-01` 이후 처음으로 Claude API의 새 버전 `2026-10-21`을 내고, 이 버전을 기본으로 보내는 SDK·CLI 새 메이저 버전을 함께 공개했다.

기준 시점: 2026-10-21

## 무슨 일인가

앤트로픽 릴리스 노트에 따르면 2026년 10월 21일 API 버전 `2026-10-21`을 공개했다. Claude API는 요청마다 `anthropic-version` 헤더를 보내야 하고, SDK는 이 헤더를 대신 채운다. 버전 문서의 이력에는 `2023-01-01`(최초), `2023-06-01`, 그리고 이번 `2026-10-21` 세 개가 있다.

버전 문서는 한 버전 안에서 지키는 약속도 적어 두었다. 기존 입력·출력 파라미터는 유지하고, 대신 선택 입력 추가·출력 값 추가·에러 조건 변경·열거형 출력 값(예: 스트리밍 이벤트 타입)의 새 변형 추가는 할 수 있다고 밝힌다. 이번 버전은 그 범위를 넘는, 기존 코드를 깨는 변경을 모은 것이다.

마이그레이션 가이드가 밝힌 Messages API의 깨지는 변경은 세 가지다.

- `assistant` 메시지에 `document` 블록을 직접 넣으면 400 오류. 문서는 `user` 메시지로 보내야 한다(웹 페치 툴 결과처럼 다른 블록 안에 든 문서는 여전히 허용).
- `user` 메시지의 `text` 블록에 비어 있지 않은 `citations` 배열을 넣으면 400 오류.
- `temperature`, `top_p`, `top_k`가 제거됐다. 기본값을 보내도 400 오류다. 가이드는 Claude 4.7 이후 모델은 원래 기본값만 받으므로 동작이 같고, Claude Sonnet 4.6처럼 다른 값을 받던 모델에서 `temperature`를 낮춰 일관성을 얻던 요청은 그 효과를 잃는데 대체 설정은 없다고 밝혔다. 그런 요청은 파라미터를 빼거나 `2023-06-01`에 남겨 두라고 안내한다.

Admin API와 Claude Enterprise Analytics API는 필드 이름이 바뀌었다(`roles` → `role_ids`, `name` → `display_name`, API 키의 `workspace_id` → `scope.workspace_id`, `actor.email` → `actor.email_address` 등).

SDK와 CLI도 새 메이저 버전이 나왔다. Python SDK 2.0.0, TypeScript SDK 1.0.0, C# SDK 13.0.0, Go SDK 2.0.0, Java SDK 3.0.0, PHP SDK 1.0.0, Ruby SDK 2.0.0, `ant` CLI 2.0.0이 `2026-10-21`을 기본으로 보낸다. 가이드에 따르면 SDK를 쓰면 요청은 "그 SDK 메이저 버전이 나올 때의 현재 API 버전"을 쓴다. 이 SDK들에는 API 버전과 무관한 깨지는 변경도 있다. API 키를 `X-Api-Key` 대신 `Authorization: Bearer` 헤더로 보내게 바뀌어, `X-Api-Key`를 읽거나 넣는 프록시·게이트웨이를 고쳐야 한다고 밝혔다. Go 모듈 경로는 메이저 2 규칙에 따라 `.../anthropic-cli/v2`가 됐고, 라이선스는 MIT에서 Apache 2.0으로 바뀌었다(이전 버전은 MIT 유지).

Amazon Bedrock에서는 `2026-10-21`이 Claude 4.7 이후 모델에만 제공된다. 그 이전 모델을 부르는 코드는 지금 쓰는 API 버전과 SDK 버전에 그대로 두라고 안내한다.

## 왜 중요한가

API를 쓰는 쪽에서 가장 무서운 건 어느 날 요청이 갑자기 400을 받는 일이다. 날짜 기반 버전을 헤더로 고정하는 방식은 이 위험을 클라이언트 손에 넘긴다. 헤더를 `2023-06-01`로 보내는 코드는 이번 변경과 상관없이 그대로 돌고, 새 동작이 필요할 때 헤더(또는 SDK 메이저 버전)를 올리면서 깨지는 변경을 한 번에 처리한다. 3년 넘게 한 버전을 유지하다가 깨지는 변경을 한 묶음으로 낸 것도 같은 원리다.

에이전트를 만드는 쪽에서는 샘플링 파라미터 제거가 눈에 띈다. `temperature`를 0 근처로 두고 "결정적인 출력"을 기대하던 설계는 새 버전에서 쓸 수 없다. 앤트로픽은 대신 쓸 설정이 없다고 밝혔으므로, 일관성은 프롬프트·구조화 출력·검증 단계 쪽에서 확보해야 한다.

## 짚고 갈 개념

- API 버저닝 — 깨지는 변경을 새 버전으로 묶고 클라이언트가 버전을 골라 고정하게 하는 방식, 날짜 기반 헤더 방식과 URL 경로 방식의 차이
- 시맨틱 버저닝 — SDK가 메이저 버전을 올려 깨지는 변경을 알리는 규칙, Go 모듈의 `/v2` 경로 규칙
- [[API Gateway]] — 인증 헤더가 `X-Api-Key`에서 `Authorization`으로 바뀌면 중간에서 헤더를 읽고 붙이는 게이트웨이·프록시 설정도 함께 바꿔야 한다

## 내 생각

버전 문서가 "입력·출력은 유지하되 출력 값과 열거형 변형은 늘어날 수 있다"고 적어 둔 부분이 실무에서 더 중요해 보인다. 같은 버전 안에서도 스트리밍 이벤트 타입이 새로 생길 수 있다는 뜻이라, 모르는 이벤트 타입을 만나면 무시하고 넘어가는 클라이언트가 아니면 버전을 고정해도 깨질 수 있다. SDK 업그레이드에 API 버전 변경과 SDK 자체 변경(인증 헤더, 타입 구조)이 한꺼번에 실려 온다는 점도, 둘을 나눠 테스트해야 원인을 찾기 쉬울 것으로 보인다.
